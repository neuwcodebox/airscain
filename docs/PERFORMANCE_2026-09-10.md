# 대규모 난전 병목 분석 — 2026-09-10

대규모 난전에서는 **게임 계산과 렌더링 양쪽이 예산을 넘는다.** 계측 없는 CPU는 50ms 게임 진행당 평균 **51.6–55.0ms**다. GPU 타이머 없는 실제 창의 고정 부하 프레임은 평균 **391ms**, p95 **668ms**, 최대 **820ms**였다. 주요 계산은 미사일 포대, 기관포 탄도, 레이더 항적 연관이고, 렌더링에서는 **GPU 입자와 2048² 연기 그림자 추가 패스**의 큰 비용을 반복 확인했다. 기존 생성 예열이나 단일 질의 최적화만으로 남은 지속 부하를 해소하기 어려운 구조다.

| --- | ---: | ---: |
| 자산 / 최대 접촉 / 최대 항적 | 12 / 186 / 120 | 45 / 364 / 303 |

기본→대형에서 자산은 3.75배, 최대 접촉은 약 1.96배이며 평균 CPU는 실행 평균 기준 **약 6배**다. 자산과 위협을 동시에 늘린 비교이므로 어느 한 개체 수만의 복잡도를 실증한 스케일링 곡선은 아니다. 상세 계측 평균 56.673ms와 계측 없는 평균 53.620ms의 차이 약 3.1ms에는 계측 비용과 실행 편차가 섞인다.

## 측정 조건과 해석

대상은 `a7e08a3`의 게임 코드다. 이번 변경은 진단 도구와 문서이며 게임 로직·품질·밸런스를 변경하지 않는다. Ryzen 7 5800X, RTX 3060, WSL, Godot 4.7.2, Compatibility/Mesa D3D12의 로컬 실행이다. 실제 창은 1600×900, MSAA 2×, 3D 해상도 배율 1, 프레임 제한 0을 사용한다. 사용자 설정은 저장하지 않고 진단 프로세스에서만 기본값으로 덮어쓴다. V-Sync 해제는 요청하지만 이 드라이버는 변경 미지원 경고를 출력한다. 웹 빌드와 다른 PC의 FPS로 일반화하지 않는다.

`tools/profile_check.gd`의 seed 73129, 20초 고정 공습을 사용했다. 기본 부하는 자산 종류별 1세트, 대형은 4세트와 위협 종류별 20기다. 부하 재현용 격자 배치이므로 최적 방어 배치나 특정 사용자의 저장 파일은 아니다. 생성·배치·예열 시간은 CPU 표본에서 제외한다. 오디오 드라이버는 Dummy이고 전투·UI 재생도 비활성화한다.

- **CPU 표본**: `main._process(0.05)` 호출 400회. 각 호출은 게임 규칙대로 25ms 하위 단계 2회로 나뉜다. 표의 ms는 **50ms 게임 진행당 비용**이며 화면 FPS가 아니다. 독립 자식 노드의 `_process`, 렌더링, 실제 오디오 재생은 포함하지 않는다. 동기 signal로 호출된 표시 갱신은 호출자의 시간에 포함한다.
- **상세 비용**: `--breakdown --detail --geometry`. 상위 모듈과 내부 호출은 inclusive time이다. 예를 들어 항적 연관 시간은 레이더에, C2 조회·기관포 탄도는 방어체계에 이미 포함된다. 내부 값을 상위 값에 다시 더하지 않는다. 상세 계측은 시계·Dictionary·함수 호출 오버헤드를 추가하므로 계측 없는 대조군도 별도로 실행한다.
- **실제 창 프레임**: `--render`. 같은 400회 게임 진행에서 `process_frame`과 `frame_post_draw`까지 경과한 시간을 기록하고 첫 20프레임을 제외한다. 프레임 완료 신호까지의 wall time이며 GPU만의 시간이 아니다. 게임은 표본마다 고정 50ms 진행하므로 자동 실시간 루프의 FPS와도 구별한다.
- **렌더 제외 실험**: `--render-probe`. 20초 시점의 게임·표현 노드 처리를 멈추고 GPU 파티클의 `speed_scale`을 0으로 만든다. 각 조건은 10프레임 안정화 후 30프레임을 측정한다. 제외 전후에 원래 장면을 재측정하고 두 번째 반복에서는 조건 순서를 뒤집는다. 표시 대상·입자 수·기하량이 같은지 draw call과 primitive 수를 함께 확인한다. 물·하늘 등의 셰이더 `TIME`까지 멈추는 실험은 아니다.
- **제외 효과 해석**: 각 제외 구간 전후의 원래 장면 평균을 기준으로 차이를 계산한다. 제외 조건끼리 겹치는 비용이 있으므로 차이를 합산하지 않는다. `no_particles`에는 GPU 연기 그림자 proxy도 포함된다. `no_trails`는 MultiMesh 궤적과 그 자식 그림자다. `cached_smoke_map`은 이미 그린 연기 그림자 텍스처를 유지한 채 2048² 별도 viewport 갱신만 중단하며 수신 표면의 셰이딩은 유지한다. `no_ui`는 CanvasLayer만 숨기므로 3D 항적 표식은 남는다.
- **GPU 계측**: `--gpu-timing`은 엔진의 주 viewport CPU/GPU 계측을 추가한다. CPU·GPU가 겹치거나 드라이버 대기가 포함되므로 두 값을 합산하거나 전체 프레임을 정확하게 분해하는 데 사용하지 않는다. 타이머 없는 실제 창 실행도 대조한다.

## CPU 병목: 탄도 전수 검사·표적 평가·항적 연관

상세 계측 실행은 평균 **56.673ms**, p95 **123.687ms**, 최대 **187.764ms**였다. 최대 접촉 364개·항적 303개·자산 45개·기관포 비행탄 158발이며, 종료 시 접촉 206개·항적 143개·도시 기능 8,520이다. 계측 없는 대형 실행과 전투 지표가 일치했다. `projectiles=161`은 발사체 부모의 최대 child 수이므로 잔류 효과까지 포함하며 실제 동시 비행탄 수가 아니다.

**기관포는 표적 선택보다 탄도 검사가 비싸다.** [`defense/close_in_gun/gunfire_runtime.gd`](../defense/close_in_gun/gunfire_runtime.gd)의 `_step()`은 모든 활성 표적의 위치·속도를 모은 뒤 각 무장된 탄마다 표적 전체를 순회한다. 거리로 상세 교차 검사를 일찍 제외하지만, 후보를 찾는 전체 순회 자체는 남는다. 비용이 탄 수 × 적 수 × 적분 단계 수에 따라 커지는 구조다. 이번 25ms 하위 게임 단계도 기관포 내부에서 20ms + 5ms로 다시 나뉜다. 기관포 전체의 약 **70%**가 이 탄도 구간이고 시각 버퍼 업데이트는 약 2%다.

**미사일은 매 게임 단계마다 항적을 다시 평가한다.** [`defense/missile_battery/missile_battery.gd`](../defense/missile_battery/missile_battery.gd)의 `gameplay_tick()`은 쿨다운이 남아 있어도 가용 항적과 탄종·분류 적합도·사거리·교전 예약·고도를 평가하고 조준한다. 12개 포대 × 800 하위 단계로 표적 선택 9,600회가 나온다. 이미 발사된 요격탄의 비행·근접 검사·연기 생성도 이 포대 시간에 포함된다. `homing_interceptor.gd`의 근접/기만 표적 검사에도 활성 위협 전체 순회가 있으나, 그 함수만의 시간을 별도로 분리한 수치는 아니다.

**항적 연관은 매 관측마다 전체 항적을 순회한다.** [`tracking/player_knowledge.gd`](../tracking/player_knowledge.gd)의 `_associate()`는 예측 위치와 게이트를 비교한다. 가까운 최선 후보보다 먼 항적의 정밀 검사는 생략하지만 전체 후보 방문은 여전히 필요하다. 관측 제출 전체는 7.096ms이며 그중 연관이 6.056ms다. 0.15초 고고도 스캔과 0.4초 저·중고도 스캔이 같은 초기 위상으로 시작해 여러 센서의 비용이 한 단계에 모일 수 있다. 느린 상위 20개 단계의 평균 CPU는 **145.487ms**, 그중 레이더 합계는 **50.529ms**였다. 최악 단계에서는 고고도 46.366ms + 저·중고도 33.322ms가 함께 발생했다. 다만 기관포·무기 발사/효과 생성도 느린 단계에 포함되므로 모든 순간 지연을 레이더 탓으로 돌리지는 않는다.

**C2는 정기 tick만 보면 비용을 놓친다.** [`c2/c2_network.gd`](../c2/c2_network.gd)의 `available_tracks_for()`는 각 무기 요청마다 로컬·공유 항적을 순회하고, `_reachable_sensor_ids()`는 캐시 조회 전 전체 endpoint의 위치·가동 상태를 확인한다. 0.002ms의 C2 tick과 달리 실제 무기 경로의 항적 조회는 5.302ms다. 여기에 앞단 `PlayerKnowledge.get_active_tracks()`의 새 배열 생성도 있지만 별도 시간으로 분리하지 않았다.

지형 높이는 **1,084,724회 / 평균 2.315ms**, 지형 선분 충돌은 126,307회 / 1.167ms, 건물 선분 충돌은 166,690회 / 0.358ms, 건물 가림 조기 판정은 6,206회 / 0.017ms였다. 지형 선분 충돌 안에 높이 질의가 다시 포함되므로 이 시간을 단순 합산하지 않는다. 호출량은 크지만 이번 측정에서는 탄도 전체·항적 연관·무기 평가보다 우선순위가 낮다.

## 렌더 병목: 입자와 연기 그림자 추가 패스

GPU 타이머 없는 실제 전투 380프레임은 평균 **391.052ms**, 중앙값 **364.065ms**, p95 **667.912ms**, 최대 **819.798ms**였다. GPU 타이머를 켠 별도 실행은 평균 **358.389ms**, p95 **649.960ms**였다. 두 실행은 동일한 최종 접촉·항적·도시 기능을 기록했지만 실제 시간에 따라 변하는 VFX 상태와 드라이버 편차가 있으므로 33ms의 차이를 타이머 효과나 성능 개선으로 해석하지 않는다.

최대 프레임 819.798ms에서 직접 측정한 `main._process(0.05)`는 **59.991ms**였다. 나머지 약 760ms는 그 호출 밖의 표현·렌더·드라이버/대기 경로이며, 전부 GPU 시간이라고 부를 수는 없다. 또한 초기 표본에서는 고고도 레이더 호출이 동기 항적 표시 갱신을 포함해 **449.069ms** 걸린 구간이 있었고 해당 게임 호출 전체는 496.795ms였다. 이 초기 구간은 위 프레임 통계의 첫 20프레임 제외에 포함되므로, 평균만 보고 최초 대량 관측 지연이 없다고 해석하지 않는다. 연관 알고리즘만의 449ms를 측정한 것은 아니다.

게임 계산을 멈춘 20초 장면도 원래 화면의 구간별 평균이 **118.170–172.103ms**, 그 중앙값이 **145.065ms**였다. 같은 draw call·primitive 수에서도 이 정도 드라이버/실행 환경 편차가 발생하므로 작은 단일 차이를 병목으로 확정하지 않는다.

정지 장면에는 접촉 206개·항적 143개, 연기 궤적 63개/활성 puff 18,016개, 보이는 GPU 파티클 노드 100개/설정 슬롯 18,038개, OmniLight 노드 46개, 적 부모 아래 MeshInstance 486개가 있었다. 슬롯·노드 수는 화면에서 실제로 유효한 입자·광원·draw 수와 같지 않다. 원래 화면은 **2,036 draw call, 1,915,280 primitive**를 제출했다.

구체적인 코드 경로:

1. [`world/smoke_shadow_projection.gd`](../world/smoke_shadow_projection.gd)의 `update_projection()`은 연기 caster가 있으면 **2048×2048 별도 viewport를 매 프레임** 렌더한다. 활성 여부 검사는 0.1초 간격이지만 실제 맵 렌더는 10Hz가 아니라 `UPDATE_ALWAYS`다. 맵 재생성을 중단하면 draw는 2,036→1,954로 82개 줄고 primitive는 **1,915,280→421,808**로 약 **78%** 줄었다. 화면 해상도를 낮춰도 이 별도 pass는 작아지지 않는다.
2. [`effects/shadowed_smoke_particles.gd`](../effects/shadowed_smoke_particles.gd)는 가시 연기와 별도로 같은 amount의 GPU 그림자 proxy를 생성한다. GPU 입자 제외는 이 proxy까지 제거하므로 입자 합성·처리·그림자 제출이 섞인 비용이다. 이를 순수 fragment 셰이더 비용이라고 해석하면 안 된다.
3. [`effects/explosion/explosion.gd`](../effects/explosion/explosion.gd)는 화구·연기·파편·섬광과 국소광을 함께 운용한다. 입자와 광원을 같이 제외한 결과는 단독 제외를 합친 값과 같지 않다. 동시 효과의 상호작용을 별도 최적화 대상으로 봐야 한다.
4. [`ui/altitude_profile.gd`](../ui/altitude_profile.gd)는 항적마다 원/외곽선, 요격체마다 다각형/외곽선을 그린다. CanvasLayer 전체를 숨기면 draw가 **2,036→1,582**로 454개 줄었다. UI 갱신 함수의 CPU 비용이 작더라도 UI 렌더 제출 비용은 남는다. 이 454개 전부를 고도 프로파일 단독 비용이라고 확정한 측정은 아니다.

이 결과는 **렌더 제출·입자·별도 그림자 패스의 복합 병목**을 지지한다. 해상도 축소 결과만으로 GPU 비용이 없다고 결론 낼 수도 없고, 단순 픽셀 overdraw만 주원인이라고 단정할 수도 없다. 정지 장면에서 캐시된 그림자를 사용한 것은 진단용 대조군이다. 실제 이동 중인 연기 그림자를 그대로 캐시하는 최적화를 구현한 결과는 아니다.

## 개선 우선순위와 남은 확인 범위

구조 변경과 일반 최적화 기법을 [난전 최적화 후보](PERFORMANCE_OPTIMIZATION.md)에 정리했다. 첫 독립 실험은 **연기 그림자의 깊이 임포스터화**와 **기관포의 공간 후보 검색**이고, 다음은 **C2 항적 조회 공유**와 **관측→항적 연관 검색**이다. 후보별 코드 경로, 보존할 규칙, 시각·시간 정책의 영향, 검증 기준과 참고 자료는 후보 문서에서 관리한다. 이 보고서는 최적화 전 기준이며, 실제 채택·전후 검증은 [구현 결과](PERFORMANCE_IMPLEMENTATION.md)에서 관리한다. 이번 제외 실험의 감소율을 제품 최적화 예상치로 간주하지 않는다.

도시와 UI도 후속 조사 대상이다. UI 정기 갱신이 싸더라도 CanvasLayer 제외 시 454개의 draw가 줄었지만, 이번 측정의 주병목보다 기여는 작았다. 기체·태양 그림자 단독 제외는 반복 편차가 커 우선순위를 확정하지 않는다.

[`main/main.gd`](../main/main.gd)의 실제 루프는 받은 `delta × simulation_speed`를 최대 1/30초 단위로 전부 나눠 계산한다. 따라서 긴 프레임이나 배속에서는 한 화면 프레임에 수행할 게임 단계가 증가하는 구조다. 이번 고정 50ms 진단은 그 피드백을 포함하지 않으며, 실시간 자동 루프의 지연을 과소평가할 수 있다. 배속·장기 작전·사용자 저장 파일의 별도 측정 없이는 그 증폭 정도를 수치로 확정하지 않는다.

## 재현 명령

성능 실행끼리는 동시에 돌리지 않는다. CPU 기준은 기본·대형을 각각 독립 반복한다.

```bash
godot --headless --audio-driver Dummy --path . --script res://tools/profile_check.gd
godot --headless --audio-driver Dummy --path . --script res://tools/profile_check.gd -- --large
godot --headless --audio-driver Dummy --path . --script res://tools/profile_check.gd -- --large --breakdown --detail --geometry
godot --audio-driver Dummy --path . --script res://tools/profile_check.gd -- --large --breakdown --render
godot --audio-driver Dummy --path . --script res://tools/profile_check.gd -- --large --breakdown --render --render-probe --gpu-timing
```

`PROFILE_*` 행이 원본 측정값이다. `--breakdown`은 단계별 비용을 `/tmp/airscain_profile_steps.json`에, `--render`는 실제 전투 화면을 `/tmp/airscain_profile_combat.png`에 쓴다. 다음 실행이 덮어쓰므로 보존하려면 실행 직후 복사한다. p95는 정렬한 표본의 `floor(n × 0.95)` 위치다. 장기 작전·다중 seed·야간·배속·오디오·웹은 별도 측정 대상이다.

이번 8개 실행의 원본 `PROFILE_*` 행, 20개 제외 비교의 계산값과 느린 단계 추적 요약은 [PERFORMANCE_2026-09-10.json](PERFORMANCE_2026-09-10.json)에 보존한다. 실험 중 진단용 scene 교체가 export 값을 초기화한 실행은 제외하고, export 보존을 수정한 최종 상세 실행만 채택했다. 헤드리스 최종 상세/일반 대형 실행은 최대 접촉·항적·기관포 탄수 및 최종 접촉·항적·도시 기능이 일치한다. 실제 창은 최대 기관포 탄수 161발로 헤드리스의 158발과 다르므로 두 실행의 전체 상태가 동일하다고 주장하지 않는다. 잔류 효과 수 역시 실제 프레임 시간에 따라 달라질 수 있다.

검증: 최종 진단기 check-only, Godot 메타데이터 생성, 8개 채택 실행의 스크립트/런타임 오류 검사, 원본 JSON 구조와 diff 검사 통과. 실제 1600×900 전투 캡처를 확인했다. 기존 정찰 비행의 colinear 방향 경고와 WSL V-Sync 변경 미지원 경고는 기록에 남아 있다. 게임 구현은 변경하지 않아 전체 게임 회귀 테스트를 재실행하지 않았다.
