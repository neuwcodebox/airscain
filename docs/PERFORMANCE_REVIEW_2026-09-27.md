# 플레이 중 지연과 대규모 전투 성능 검토

## 현재 판단

우선 해결할 문제는 **동시 효과의 지속적인 렌더 비용**과 **실전 부하를 제대로 재현하는 진단 기준의 부재**다. 기존 예열은 첫 등장에 따른 큰 지연을 줄였지만, 같은 효과가 동시에 많이 보일 때의 프레임 비용은 남는다. 게임 루프는 느린 프레임의 경과 시간을 모두 하위 단계로 따라잡으므로 렌더 지연이 다음 프레임의 게임 계산량을 키울 가능성도 있다. 이 연결은 현재 실시간 자동 루프로 계측하지 않았으므로 가설로 남긴다.

이번 검토는 성능 개선 구현을 포함하지 않는다. 기존 결과는 [대규모 교전 분석](PERFORMANCE_2026-09-10.md), [적용 결과](PERFORMANCE_IMPLEMENTATION.md), [순간 지연 측정](PERFORMANCE.md), [웹 첫 등장 측정](PERFORMANCE_WEB_HITCH.md)에 있다. 그 결과와 이번 측정의 부하가 다르므로 개선율로 직접 비교하지 않는다.

## 이번에 확인한 근거

2026-09-27, Godot 4.7.2, WSL/Mesa D3D12 RTX 3060, Compatibility 실제 창, Dummy 오디오, seed 73129의 자유 모드에서 `tools/hitch_check.gd -- --brief`를 실행했다. 앱과 전장 효과 예열 후 시뮬레이션을 멈추고 사건마다 10프레임 안정화, 12프레임 완료 간격을 잰다. 폭발 표본은 `ExplosionEffect.spawn()`의 직접 호출이므로 일반 전투의 모든 상태 변경을 포함하지 않는다.

16·32개 폭발은 첫 프레임 이후에도 여러 프레임이 계속 느렸다. 따라서 폭발 객체 생성 시간만 줄이는 조치로는 이 현상을 설명하거나 해결하기 어렵다. 앞선 실행에서도 16개는 최대 270.2/273.5ms, 32개는 486.8/505.7ms였지만 실행 사이 편차가 있어 단일 최대치의 작은 차이를 해석하지 않는다. 이 값은 GPU 전용 시간이 아니라 `process_frame`과 `frame_post_draw`를 기다린 시간이며, 카메라·효과 중첩·드라이버 조건을 달리한 실제 FPS를 보장하지 않는다. 이번 실행에서 표적 지식이 필요한 레이더 타격기는 생성이 거부되어 표본으로 사용할 수 없었다. 진단 도구는 이 경우를 명시적으로 건너뛰도록 수정했고 재실행에서 런타임 오류 없이 종료했다.

현재 `tools/profile_check.gd -- --large`의 headless 고정 20초 표본은 53개 방어 자산, 최대 접촉 182개, 최대 항적 98개, **최대 기관포 비행탄 0발**이었다. 50ms 게임 진행당 CPU 평균 17.031ms, p95 29.890ms, 최대 44.463ms였지만 기관포 난전의 기준선으로는 부적합하다. 2026-09-10의 45개 자산·최대 접촉 364개·최대 항적 303개·최대 기관포 탄 158발과 부하 구성이 다르다. 현재 수치를 과거 최적화의 추가 개선율이나 대규모 실전 성능으로 해석하지 않는다.

기존 동일 부하 비교에서는 기관포 공간 후보 검색, C2 조회 공유, 항적 연관 검색으로 대형 고정 진행 CPU 평균이 53.177→42.146ms 감소했다. 실제 창의 전후 한 번씩 비교는 410.228→377.484ms였지만 최대 지연은 889.950→910.331ms로 악화됐다. 과거 정지 장면에서 입자 제외는 프레임 시간을 약 34–36%, 연기 그림자 맵 갱신 중단은 약 21–30% 줄였다. 이 제외 실험은 실제 채택 가능한 변경의 예상 개선율이 아니며 비용이 서로 겹친다. 그림자 깊이 임포스터는 기하량 감소에도 전체 프레임 개선이 반복되지 않아 보류됐다.

## 개선 실행 순서

### 1. 측정 기준과 순간 지연의 귀속

- 고정 난전 표본에 실제 기관포 발사, 미사일 발사, 센서 관측, 도시 타격, 동시 VFX가 발생하도록 배치와 시간을 재설계한다. 각 실행은 발생 건수·최대 동시 탄·접촉·항적·효과 수를 출력하고, 필수 부하가 0이면 실패시킨다. 기존 2026-09-10 수치는 참고 기록으로 유지하고 새 기준선을 독립적으로 세운다.
- 실제 게임 자동 루프에서 프레임 시작부터 완료까지와 `_process` 게임 계산, 자식 `_process`, 렌더 CPU/GPU 계측값을 같은 프레임 ID에 묶는다. 공습 출현, 첫 관측, 발사, 격추, 폭발, 도시 피해, 저장 복원, 낮밤 전환, 일시정지 재개 시각과 개체 수를 함께 기록한다. 평균보다 p95·p99·최대와 연속 느린 프레임 길이를 우선 본다.
- 1×·2×·4×, 일반·대형 부하, 낮·밤, 여러 seed를 분리한다. 예열 시간과 실제 플레이 프레임을 구분하고, Windows 네이티브와 WebGL에서 같은 사건을 재측정한다. 한 드라이버의 프레임 간격을 다른 플랫폼의 목표치로 사용하지 않는다.

### 2. 동시 효과 렌더 비용 축소

- 폭발 수를 1·4·16·32개로 바꾸며 입자, 국소광, 파편, 연기 그림자 맵, 본 화면 합성을 하나씩 분리해 반복 교차 측정한다. 화면 draw·primitive·활성 입자·광원·그림자 caster 수도 함께 기록한다. 현재 16·32개에서 반복되는 느린 프레임을 우선 재현한다.
- 가장 비싼 경로가 확인되면 재질·광원·그림자 갱신을 동일한 시각 결과에 가깝게 묶거나 필요한 범위만 처리하는 실험을 한다. 지역별 효과 버퍼와 연기 그림자의 집계 표현은 후보이며, 화면 밖 효과가 화면 안에 드리우는 그림자와 투명 정렬을 보존해야 한다. 단순 proxy 기하 축소나 주 화면 해상도 축소는 이전 실험에서 전체 개선이 확인되지 않았으므로 재채택 근거가 필요하다.
- 효과 개수·수명·밝기·거리별 LOD를 바꾸는 방법은 품질 정책으로 별도 비교한다. 피격과 요격 결과를 알아보는 데 필요한 표현을 유지하고 실제 창에서 가까운 교전·먼 교전·도시 위 중첩·낮은 태양·야간을 검수한다.

### 3. 게임 계산과 긴 프레임의 증폭 확인

- 유효한 난전 표본에서 포대의 매 하위 단계 `available_tracks()`·`select_track()`·탄종 평가, 레이더 동시 스캔, 기관포 남은 탄도 비용을 다시 계측한다. 포대의 현재 표적 조준과 전체 후보 재평가를 분리하는 실험은 발사 직전 유효성·우선 위협 반응·예약 규칙을 보존하는 조건으로 진행한다.
- 센서 스캔 시작 위상 분산은 총 CPU 감소가 아닌 지연 꼬리 감소 여부로 판단한다. 최초 탐지 시점, 같은 단계의 관측 합성, 저장 복원 후 스캔 시각을 함께 검증한다.
- 긴 렌더 프레임 뒤 `ceili(simulation_delta / MAXIMUM_GAMEPLAY_STEP)`가 실제로 얼마나 많은 단계를 한 프레임에 모으는지 계측한다. 결과가 지연을 키운다면 고정 tick·렌더 보간·따라잡기 한도를 설계한다. 초과 시간을 버리지 않고 게임 시간·배속 정책을 명시해야 한다.

## 채택 기준과 검증

각 변경은 같은 seed와 부하 상태가 유지되는 전후 교차 반복으로 **전체 프레임 p95·p99·연속 지연**, 게임 CPU, 렌더 CPU/GPU, 메모리·효과 수를 비교한다. 관리 비용을 포함한 전체 지표에서 반복 개선이 없으면 채택하지 않는다. 기관포 명중·탄약·피해·관측·교전 순서·저장 복원을 집중 회귀로, 표현은 실제 창의 주야간과 WebGL로 확인한다. 변경 단위마다 `docs/PLAN.md`에 결과와 남은 위험을 갱신한다.
