# 플레이 중 지연과 대규모 전투 성능 검토

## 현재 판단

우선 해결할 문제는 **동시 효과의 지속적인 렌더 비용**이다. 기존 예열은 첫 등장에 따른 큰 지연을 줄였지만, 같은 효과가 동시에 많이 보일 때의 프레임 비용은 남는다. 실제 자동 루프에서 긴 프레임 뒤 게임 단계가 집중되는 현상도 관측됐다. 같은 프레임의 렌더 시간과 게임 CPU를 분리하지 못했으므로 두 현상의 인과관계와 기여도는 아직 미확정이다.

기존 결과는 [대규모 교전 분석](PERFORMANCE_2026-09-10.md), [적용 결과](PERFORMANCE_IMPLEMENTATION.md), [순간 지연 측정](PERFORMANCE.md), [웹 첫 등장 측정](PERFORMANCE_WEB_HITCH.md)에 있다. 그 결과와 이번 측정의 부하가 다르므로 개선율로 직접 비교하지 않는다.

## 외부 근거와 프로젝트 적용

Godot 공식 [Profiler 문서](https://docs.godotengine.org/en/4.5/tutorials/scripting/debug/the_profiler.html)는 `Frame Time`이 스크립트·물리뿐 아니라 렌더링까지 포함하며, 스크립트가 빠른 프레임의 지연도 파티클이나 시각효과에서 생길 수 있다고 설명한다. [Visual Profiler 문서](https://docs.godotengine.org/en/4.5/tutorials/scripting/debug/debugger_panel.html#visual-profiler)는 렌더 CPU와 GPU 항목을 나누어 보되 동일 viewport 크기로 실행을 비교하라고 한다. 따라서 현재 `process_frame` 완료 간격만으로 GPU 병목을 단정하지 않고, 같은 프레임 ID의 게임 CPU·렌더 CPU·GPU 계측을 다음 필수 단계로 둔다.

Godot 공식 [GPU 최적화 문서](https://docs.godotengine.org/en/4.5/tutorials/performance/gpu_optimization.html)는 OpenGL·WebGL에서 API 명령과 상태 변경 비용이 크고, 겹친 투명 오브젝트는 뒤의 오브젝트까지 모두 그려 fill rate를 소모한다고 설명한다. 이 프로젝트의 폭발은 한 효과마다 여러 투명 `GPUParticles3D`, 연기 그림자용 복제 입자와 국소광을 사용한다. 입자 수 비율만 낮춘 실험이 개선되지 않은 결과와 함께 보면 다음 후보는 단순 입자 개수 조정보다 제출 단위·재질 상태·화면 중첩·그림자 pass를 분리해 측정하는 것이다. 공식 [3D 성능 문서](https://docs.godotengine.org/en/4.5/tutorials/performance/optimizing_3d_performance.html)가 권하는 거리 기반 가시 범위와 `MultiMesh`는 측정에서 해당 제출 비용이 확인될 때 적용하며, 전장 전체를 한 덩어리로 합쳐 개별 culling을 잃지 않는다.

현재 Web preset은 Godot가 기본으로 권하는 단일 스레드 내보내기다. 공식 [Web 내보내기 문서](https://docs.godotengine.org/en/4.5/tutorials/export/exporting_for_web.html)는 단일 스레드가 호환성은 높지만 다중 스레드보다 성능이 낮고, 다중 스레드는 교차 출처 격리 헤더가 필요하다고 명시한다. 따라서 웹은 네이티브와 별도 성능 예산으로 검증한다. 스레드 전환은 정적 호스팅·외부 삽입 호환성을 포함한 별도 제품 결정으로 남기며 현재 개선책의 전제로 삼지 않는다.

Firefox 경고에 나타난 `getBufferSubData()`는 Khronos [WebGL 2.0 명세](https://registry.khronos.org/webgl/specs/latest/2.0/#5.14.5)에 따라 앞선 GPU 쓰기가 끝나야 결과를 돌려주는 차단 연산이며 프로세스 간 왕복도 일으킬 수 있다. 다만 현재 측정은 호출 스택이나 호출 횟수를 확보하지 못했다. 폭발 지연과의 인과관계는 Firefox 프로파일에서 호출 시각이 느린 프레임과 일치하고 해당 경로를 제거한 교차 실험이 개선될 때만 확정한다.

## 이번에 확인한 근거

2026-09-27, Godot 4.7.2, WSL/Mesa D3D12 RTX 3060, Compatibility 실제 창, Dummy 오디오, seed 73129의 자유 모드에서 `tools/hitch_check.gd -- --brief`를 실행했다. 앱과 전장 효과 예열 후 시뮬레이션을 멈추고 사건마다 10프레임 안정화, 12프레임 완료 간격을 잰다. 폭발 표본은 `ExplosionEffect.spawn()`의 직접 호출이므로 일반 전투의 모든 상태 변경을 포함하지 않는다.

| --- | ---: | ---: | --- |
| 유휴 | 0.006ms | 26.4ms | 이 실행의 장면 기준 |
| 폭발 1개 | 0.25–0.33ms | 42.1 / 41.5ms | 첫 생성 지연이 주원인으로 보이지 않음 |

16·32개 폭발은 첫 프레임 이후에도 여러 프레임이 계속 느렸다. 따라서 폭발 객체 생성 시간만 줄이는 조치로는 이 현상을 설명하거나 해결하기 어렵다. 앞선 실행에서도 16개는 최대 270.2/273.5ms, 32개는 486.8/505.7ms였지만 실행 사이 편차가 있어 단일 최대치의 작은 차이를 해석하지 않는다. 이 값은 GPU 전용 시간이 아니라 `process_frame`과 `frame_post_draw`를 기다린 시간이며, 카메라·효과 중첩·드라이버 조건을 달리한 실제 FPS를 보장하지 않는다. 이번 실행에서 표적 지식이 필요한 레이더 타격기는 생성이 거부되어 표본으로 사용할 수 없었다. 진단 도구는 이 경우를 명시적으로 건너뛰도록 수정했고 재실행에서 런타임 오류 없이 종료했다.

첫 점검 당시 `tools/profile_check.gd -- --large`의 headless 고정 20초 표본은 53개 방어 자산, 최대 접촉 182개, 최대 항적 98개, **최대 기관포 비행탄 0발**이었다. 배치가 전장 한쪽에 몰리던 진단 오류를 고쳤다. 2026-09-10의 45개 자산·최대 접촉 364개·최대 항적 303개·최대 기관포 탄 158발과도 부하 구성이 다르므로 이전 수치를 새 기준선의 개선율로 해석하지 않는다.

기존 동일 부하 비교에서는 기관포 공간 후보 검색, C2 조회 공유, 항적 연관 검색으로 대형 고정 진행 CPU 평균이 53.177→42.146ms 감소했다. 실제 창의 전후 한 번씩 비교는 410.228→377.484ms였지만 최대 지연은 889.950→910.331ms로 악화됐다. 과거 정지 장면에서 입자 제외는 프레임 시간을 약 34–36%, 연기 그림자 맵 갱신 중단은 약 21–30% 줄였다. 이 제외 실험은 실제 채택 가능한 변경의 예상 개선율이 아니며 비용이 서로 겹친다. 그림자 깊이 임포스터는 기하량 감소에도 전체 프레임 개선이 반복되지 않아 보류됐다.

## 실행 결과

진단 배치를 전장 중앙부터 채우고 대형 20초 표본에 기관포 비행탄·발사와 미사일 발사가 없으면 실패하도록 했다. 새 표본은 최대 접촉 176개·항적 111개·기관포 비행탄 166발, 기관포 발사 1,415발·미사일 발사 107발, 일괄 관측 8,657건이다. 계측 없는 headless CPU는 50ms 게임 진행당 평균 20.993ms, p95 35.963ms였다. 실제 창의 같은 배치에서는 평균 프레임 336.285ms, p95 604.646ms였으며 발사 수와 최종 상태에 약간의 렌더 경과 시간 차이가 있었다. 두 수치는 동일 시계의 FPS가 아니다.

정지 난전 장면에서 입자를 제외하자 평균 프레임은 약 154→102ms였고, 16개 폭발만 고정한 장면에서 모든 입자를 제외하자 약 102→46ms였다. 폭발의 개별 연기·화구·파편·광원·그림자 맵을 제외한 비용은 실행 순서와 드라이버 편차가 섞여 있다. 입자 `amount_ratio`를 동시 폭발 수에 따라 줄이는 제품 실험은 실제 16·32개 폭발 프레임을 줄이지 못해 되돌렸다. 진단에서 입자 버퍼의 `amount` 자체를 절반으로 낮춰도 16개 최대 208/310ms, 32개 최대 368/491ms로 기준 변동 범위를 벗어나는 안정적 개선이 없어 채택하지 않았다. 이 결과는 입자 제출·합성 구조를 다음 후보로 삼는 근거이며, 특정 파티클 종류의 절대 GPU 시간을 뜻하지 않는다.

연기 그림자 투영은 caster 유무를 0.1초마다 확인하면서도 활성화되면 2048² SubViewport를 매 화면 프레임 렌더하고 있었다. 이를 같은 10Hz의 `UPDATE_ONCE`로 바꿨다. 한 실행 안에서 16개 정지 폭발의 연속 갱신은 평균 87.9/93.9ms, 완전 캐시는 73.3/79.8ms였고, 10Hz 전체 장면의 대표 구간은 대체로 77~84ms였다. 실행 순서 편차 때문에 단일 개선율은 정하지 않지만 두 반복에서 연속 갱신보다 낮아 변경을 채택했다. 실제 캡처는 비행 궤적과 피해 연기의 지면 그림자·감쇠를 유지했다. 기존 `cached_smoke_map` 진단은 투영 노드가 0.1초 뒤 viewport를 다시 켜는 오류가 있어, 이제 노드 처리까지 정지한 상태로 캐시 비용을 잰다. 모든 입자 제외는 여전히 31.7~38.4ms로 가장 큰 차이를 보여 다음 후보는 본 화면 입자 제출·합성이다.

활성 순서에 따른 상세도 차등은 사용하지 않는다. 모든 폭발이 화구 두 층, 불꽃·파편·연기와 그림자, 섬광·광륜·압력파·충격파를 같은 규칙으로 표시한다. 실제 폭발 점광원은 반경에 맞춰 확장하는 방사형 additive card로 교체해 HDR emission과 환경 glow만으로 광원처럼 보이게 했다. 파편은 emitter 하나를 유지하면서 긴 속도 정렬 막대를 짧고 회전하는 금속 조각으로 바꾸고, 조각 전체가 백열색에서 어두운 금속색으로 식게 했다. 이어서 보존된 폭발의 화구 두 층을 월드 공간 `MultiMesh` 하나에 모았다. 폭발마다 카드 52장, 색·반경·수명·온도 변화와 노이즈 침식을 그대로 적용하며 순서나 동시 개수에 따른 생략은 없다. 공용 배치의 월드 원점 기준 투명 정렬로 개별 연기가 화구와 섬광 위에 그려지던 문제는 연기→화염→광륜→섬광의 render priority로 해결했다. 백열 핵의 가독 시간을 늘리고 화염 온도 램프가 주황 화구 뒤에 잔연으로 넘어가도록 조정했다. 실제 풀 경로의 단일 단계와 Compatibility 낮·밤 16개 캡처에서 확인했다. 배치 직후 24프레임의 16개 평균/중앙값/최대는 253.8/260.2/291.7ms, 32개는 435.2/455.7/531.4ms였고 직전 동일 구성보다 평균이 각각 16.4%, 20.9% 줄었다. 시각 수정 후 별도 실행은 16개 205.5/215.9/228.9ms, 32개 366.8/390.3/400.6ms로 회귀가 없었지만 실행 편차가 있어 추가 개선율로 해석하지 않는다. 연기·그림자와 파편 emitter는 독립 제출로 남아 있다.

`PlayerKnowledge._associate_scan()`은 같은 관측·항적 쌍의 비용을 후보 수집과 행렬 구성에서 다시 계산했다. 유효 비용을 첫 계산에서 보존해 사용하도록 바꿨다. 기준→수정→수정→기준 교차 실행의 연관 비용은 **1.372/1.344→0.999/0.997ms**, 전체 CPU는 **21.335/21.013→20.843/20.816ms**였다. 모두 50ms 게임 진행당 평균이고 수정판의 관측·후보·발사 수와 최종 전투 결과가 기준과 같았다. 항적·공간 검색 단위 33개, 플레이·저장 복원 통합 156개 테스트가 통과했다. 이 코드 변경의 실제 창 전후·Windows·WebGL 성능은 아직 측정하지 않았다.

C2 항적 조회는 이미 만든 장비별 view를 복사하면서 토폴로지 상태도 무기마다 다시 훑었다. 지원·재배치가 끝난 뒤 게임 단계당 한 번 토폴로지를 검증하고, 해당 단계의 무기는 읽기 전용 view를 공유하도록 바꿨다. 외부 조회와 C2 테스트 대역은 기존 복사 API를 유지한다. 40개 자산·200개 항적의 프로세스 내 교차 측정에서 100회 조회 묶음 평균은 기존 방식 0.456~0.491ms, 단계 공유 방식 0.072~0.078ms였으며 checksum은 800,000으로 같았다. 대형 난전의 중첩 비용도 토폴로지 0.705~0.734→0.069~0.085ms, 전체 C2 항적 조회 1.064~1.126→0.324~0.379ms로 줄었다. 전체 CPU 표본은 시스템 변동에 묻혀 두 방식의 범위가 겹쳤으므로 이 변경의 전체 FPS 개선율은 주장하지 않는다. 동일 난전의 관측·후보·1,415회 기관포 발사·107회 미사일 발사·최종 전투 상태는 같았다.

재현 명령은 `godot --headless --audio-driver Dummy --path . --script res://tools/profile_check.gd -- --large --breakdown --detail`과 실제 창의 `godot --audio-driver Dummy --path . --script res://tools/profile_check.gd -- --large --render --render-probe`다. 동시 폭발 분리는 `godot --audio-driver Dummy --path . --script res://tools/hitch_check.gd -- --explosion-probe`를 쓴다. 렌더 계측끼리는 동시에 실행하지 않는다. 이번 교차 실행 로그는 `/tmp/airscain_association_*.log`에 있다.

자동 루프는 `--large --live --live-frames=20 --live-speed=1`, `2`, `4`를 각각 실제 창에서 실행했다. 프레임 완료 시간의 평균/p95와 한 프레임의 최대 게임 단계는 각각 **1배속 220/581ms·5단계**, **2배속 497/1104ms·9단계**, **4배속 1652/2248ms·18단계**였다. 각 프레임의 벽시계 시간, 진행한 게임 시간, 단계 수, 접촉·항적·발사 수, draw 수는 `/tmp/airscain_live_frames.json`에 기록된다. 이 파일은 실행마다 덮어쓴다. 같은 20프레임 동안 배속별 전투가 서로 다른 게임 시점에 도달하므로 수치를 배속만의 인과 효과로 분리할 수 없다. 다만 4배속에서 하위 단계가 한 프레임에 크게 몰리는 것은 직접 관측됐다. 각 프레임의 게임 CPU와 렌더 시간을 같은 ID로 분리하는 계측은 아직 필요하다.

후속 구현에서 화면 프레임당 게임 진행을 1/30초 단계 최대 4개, 합계 0.133초로 제한했다. 초과 벽시계 시간은 작전 시간에 반영하거나 부채로 누적하지 않는다. 과부하에서는 게임 시간이 느려지며 처리된 구간의 고정 단계는 생략하지 않는다. 같은 대형 20프레임 실제 창 재측정의 평균/p95/최대 단계는 **1배속 211/540ms·4단계**, **2배속 217/550ms·4단계**, **4배속 222/593ms·4단계**였다. 기존과 새 실행은 같은 벽시계 동안 서로 다른 게임 시간을 처리하므로 이 차이를 동일 작업량의 렌더·게임 계산 개선율로 해석하지 않는다.

라이브 진단은 같은 프레임 행에 루트 게임 CPU, 전체 idle 처리, viewport 렌더 CPU/GPU, 게임 진행·단계, 접촉·항적·발사·격추·도시 피해와 draw·primitive를 기록한다. 새 20프레임 표본의 p95 렌더 CPU/GPU는 1배속 105/70ms, 2배속 106/69ms, 4배속 107/66ms였다. 게임 CPU p95는 1배속 73ms였으나 2·4배속은 첫 측정 프레임의 433/467ms 이상치가 p95가 되는 작은 표본이므로 다음 장기 측정에서 분포를 다시 판단한다.

### WebGL 재측정

2026-09-27, 같은 seed·전장·카메라와 `ExplosionEffect.spawn()` 1·16·32개를 `tools/missile_hitch_check.tscn`에서 실행했다. 임시 Web export를 Firefox 156.0, 단일 스레드 WebGL2, WSL Generic Renderer, 1600×900 캔버스에서 실행하고, 같은 장면을 WSL/Mesa Compatibility 실제 창에서도 실행했다. 유휴 12프레임 최대는 웹 42ms, 네이티브 32ms였다. 사건별 두 번의 12프레임 최대는 다음과 같다.

| 동시 폭발 | WebGL 최대 두 번 | 네이티브 최대 두 번 | WebGL 생성 CPU |
| --- | ---: | ---: | ---: |
| 1개 | 43 / 40ms | 55 / 46ms | 0–1ms |
| 16개 | 660 / 313ms | 260 / 226ms | 1ms |
| 32개 | 535 / 548ms | 545 / 461ms | 2–3ms |

웹 16개 첫 실행의 660ms는 한 프레임의 이상치다. 그 프레임을 제외해도 같은 실행의 뒤쪽 프레임은 약 235–304ms였고 두 번째 실행도 대부분 251–313ms였다. URL 옵션 검증을 위한 추가 두 실행에서 16개 최대는 279/749ms와 288/231ms, 32개는 521/547ms와 391/544ms였다. 749ms도 단일 이상치이며, 16·32개 모두 이상치를 제외한 여러 프레임이 수백 ms로 이어졌다. 웹과 네이티브 모두 생성 호출보다 이후 프레임 비용이 크므로 동시 효과 표현을 공통 우선순위로 둔다. 브라우저 콘솔에는 `getBufferSubData`의 버퍼 읽기가 파이프라인을 멈출 수 있다는 WebGL 경고가 반복됐고, 깊이 텍스처 필터 경고도 있었다. 해당 읽기의 호출 위치와 이번 폭발 지연의 연관성은 확인되지 않았다. 최종 진단 실행은 결과 7개를 기록하고 런타임 오류 없이 끝났다. WebGL은 1ms 타이머 단위이고 두 실행의 GPU 경로가 달라 수치 차이를 플랫폼별 개선율로 해석하지 않는다. 웹 대형 자동 교전, 배속, 저장 복원은 아직 미측정이다.

불꽃·파편 통합 전 별도 플랫폼 확인은 Windows 11의 Chrome 153 WebGL2와 Windows x64 네이티브 Compatibility를 사용했다. 둘 다 RTX 3060, 1600×900에서 같은 진단 Web/Windows export를 실행했다. Windows 네이티브의 동시 폭발 최대 두 번은 1개 9.6/9.6ms, 16개 10.1/11.3ms, 32개 18.1/28.5ms였고, Chrome WebGL은 10.4/10.4ms, 18.0/16.5ms, 27.0/23.8ms였다. Chrome 생성 CPU는 0.2~1.7ms이고 DevTools에서 수집한 오류는 없었다. 이 Chrome/실제 NVIDIA 결과를 앞선 Firefox/WSL Generic Renderer 수치의 개선율로 사용하지 않는다. 당시 제품 export 설정으로 Web과 Windows 내보내기가 성공했고 Web 제품 메인 메뉴가 1600×900에서 오류 없이 렌더됐다. 현재 통합판의 WSL 실제 창은 재측정했고 제품 Web release export도 성공했다. 브라우저 GPU 시간은 다시 재지 않았다.

실제 WSL Compatibility 창에서는 2배속과 일시정지의 단일 선택 상태, 작전 저장 후 메인 메뉴의 불러오기와 복원 진입, 09·17·00·06시 환경과 야간 도시 소등·복구·폭발을 다시 확인했다. 플레이 흐름 108개·2,732개 단언에는 주야간의 일시정지·배속·저장 작전 복원 회귀도 포함된다.

## 개선 실행 순서

### 1. 측정 기준과 순간 지연의 귀속

- 고정 난전 표본에 실제 기관포 발사, 미사일 발사, 센서 관측, 도시 타격, 동시 VFX가 발생하도록 배치와 시간을 재설계한다. 각 실행은 발생 건수·최대 동시 탄·접촉·항적·효과 수를 출력하고, 필수 부하가 0이면 실패시킨다. 기존 2026-09-10 수치는 참고 기록으로 유지하고 새 기준선을 독립적으로 세운다.
- 실제 게임 자동 루프에서 프레임 시작부터 완료까지와 `_process` 게임 계산, 자식 `_process`, 렌더 CPU/GPU 계측값을 같은 프레임 ID에 묶는다. 공습 출현, 첫 관측, 발사, 격추, 폭발, 도시 피해, 저장 복원, 낮밤 전환, 일시정지 재개 시각과 개체 수를 함께 기록한다. 평균보다 p95·p99·최대와 연속 느린 프레임 길이를 우선 본다.
- 1×·2×·4×, 일반·대형 부하, 낮·밤, 여러 seed를 분리한다. 예열 시간과 실제 플레이 프레임을 구분하고, Windows 네이티브와 WebGL에서 같은 사건을 재측정한다. 한 드라이버의 프레임 간격을 다른 플랫폼의 목표치로 사용하지 않는다.

### 2. 동시 효과 렌더 비용 축소

- 폭발 수를 1·4·16·32개로 바꾸며 입자, 국소광, 파편, 연기 그림자 맵, 본 화면 합성을 하나씩 분리해 반복 교차 측정한다. 화면 draw·primitive·활성 입자·광원·그림자 caster 수도 함께 기록한다. 현재 16·32개에서 반복되는 느린 프레임을 우선 재현한다.
- 가장 비싼 경로가 확인되면 재질·광원·그림자 갱신을 동일한 시각 결과에 가깝게 묶거나 필요한 범위만 처리하는 실험을 한다. 지역별 효과 버퍼와 연기 그림자의 집계 표현은 후보이며, 화면 밖 효과가 화면 안에 드리우는 그림자와 투명 정렬을 보존해야 한다. 단순 proxy 기하 축소나 주 화면 해상도 축소는 이전 실험에서 전체 개선이 확인되지 않았으므로 재채택 근거가 필요하다.
- 효과 개수·수명·밝기·거리별 LOD를 바꾸는 방법은 품질 정책으로 별도 비교한다. 피격과 요격 결과를 알아보는 데 필요한 표현을 유지하고 실제 창에서 가까운 교전·먼 교전·도시 위 중첩·낮은 태양·야간을 검수한다.

### 3. 게임 계산과 긴 프레임의 증폭 확인

- 유효한 난전 표본에서 포대의 매 하위 단계 `available_tracks()`·`select_track()`·탄종 평가, 레이더 동시 스캔, 기관포 남은 탄도 비용을 다시 계측한다. 포대의 현재 표적 조준과 전체 후보 재평가를 분리하는 실험은 발사 직전 유효성·우선 위협 반응·예약 규칙을 보존하는 조건으로 진행한다.
- 센서 스캔 시작 위상 분산은 총 CPU 감소가 아닌 지연 꼬리 감소 여부로 판단한다. 최초 탐지 시점, 같은 단계의 관측 합성, 저장 복원 후 스캔 시각을 함께 검증한다.
- 긴 렌더 프레임 뒤 `ceili(simulation_delta / MAXIMUM_GAMEPLAY_STEP)`가 실제로 얼마나 많은 단계를 한 프레임에 모으는지 계측한다. 결과가 지연을 키운다면 고정 tick·렌더 보간·따라잡기 한도를 설계한다. 초과 시간을 버리지 않고 게임 시간·배속 정책을 명시해야 한다.

## 채택 기준과 검증

각 변경은 같은 seed와 부하 상태가 유지되는 전후 교차 반복으로 **전체 프레임 p95·p99·연속 지연**, 게임 CPU, 렌더 CPU/GPU, 메모리·효과 수를 비교한다. 관리 비용을 포함한 전체 지표에서 반복 개선이 없으면 채택하지 않는다. 기관포 명중·탄약·피해·관측·교전 순서·저장 복원을 집중 회귀로, 표현은 실제 창의 주야간과 WebGL로 확인한다. 변경 단위마다 `docs/PLAN.md`에 결과와 남은 위험을 갱신한다.

첫 구현 후보의 통과 기준은 같은 플랫폼·해상도·seed의 기준/수정/수정/기준 교차 실행 네 번 모두에서 전체 프레임 p95와 연속 느린 프레임 길이가 함께 줄고, 어느 실행에서도 p99가 기준 범위보다 악화되지 않는 것이다. 60 FPS의 16.67ms와 30 FPS의 33.33ms는 결과를 읽는 기준선으로 기록하되 현재 진단 장비의 절대 수치를 제품 최소 사양 계약으로 사용하지 않는다. WebGL은 Firefox와 Chromium 계열에서 각각 측정하고 브라우저 타이머 해상도와 단일 스레드 실행 차이를 함께 기록한다.
