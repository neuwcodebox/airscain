# TECH.md

## 1. 문서 목적

이 문서는 `SPEC.md`의 최종 제품 목표를 구현하기 위한 **장기 기술 설계**를 정의한다.

다음이 이 문서의 범위다.

- 시스템과 정보 계층의 경계
- 주요 모듈과 상태 소유권
- 장면·컴포넌트·콘텐츠 구성 원칙
- 교체하기 어려운 핵심 계산 모델
- 저장, 테스트와 성능 원칙

파일명, 함수명과 세부 구현 순서는 현재 작업에 가장 적합한 방식으로 결정한다. 이 문서에 등장하는 모듈과 컴포넌트는 논리적 역할이며, 모든 골격을 미리 만들라는 뜻이 아니다. 해당 기능을 구현하는 단계에서 필요한 만큼만 도입한다.

일반적인 작업 방식과 저장소 운영 규칙은 `AGENTS.md`를 따른다.

C#, GDExtension, 별도 ECS, 멀티스레드 gameplay, 커스텀 렌더 파이프라인과 외부 런타임 플러그인은 실제 병목이나 명확한 요구가 확인된 뒤에만 도입한다.

엔진과 주요 addon 버전 변경은 별도의 명시적 작업으로 수행한다.

## 3. 아키텍처 원칙

### 3.1 게임 규칙과 표현 분리

게임 결과는 시뮬레이션 상태에서 먼저 결정한다. UI, 사운드, 파티클과 카메라 연출은 이미 확정된 상태와 사건을 표현한다.

시각효과가 피해, 보상, 탐지 또는 탄약 소모를 발생시키지 않는다.

### 3.2 정보 경계 우선

다음 세 상태는 구조적으로 구분한다.

- 실제 세계의 상태
- 플레이어 방공망이 알고 있는 상태
- 적이 플레이어 방공망에 대해 추정한 상태

이 경계는 센서, 기만, 지휘통제와 적응형 공격의 전제이므로 편의를 위해 합치지 않는다.

### 3.3 조합 우선

게임 객체는 Godot scene을 기본 단위로 하며 필요한 능력을 child node 또는 독립 script로 조합한다. 깊은 상속 계층과 하나의 범용 `Actor`·`Ability`·`Effect` 체계를 만들지 않는다.

실제 두 번째 사용 사례에서 공통점이 확인될 때만 공통 컴포넌트로 추출한다.

### 3.4 데이터 중심 콘텐츠

가격, 사거리, 탐지 특성, 탄약, 이동 특성, 피해와 시나리오 구성처럼 조정 가능한 값은 typed `Resource`로 관리한다. 동작 조합은 scene이, 조정값은 resource가 담당한다.

### 3.5 명확한 상태 소유권

각 상태에는 하나의 소유자만 둔다. 다른 모듈은 명령을 요청하거나 변화를 통지받으며 같은 값을 직접 중복 수정하지 않는다.

### 3.6 점진적 확장

최종 설계를 이유로 사용하지 않는 manager, enum, hook과 빈 데이터 필드를 미리 만들지 않는다. 현재 구현을 실행 가능한 상태로 유지하면서 세로 단면 단위로 확장한다.

## 4. 논리 계층

```text
콘텐츠 정의
    ↓
세션·시나리오·경제
    ↓
실제 세계 시뮬레이션 ─────────────┐
    ↓ 관측                         │ 사건·공개 상태
플레이어 지식과 항적               │
    ↓ 공유                         │
지휘통제와 교전                    │
    ↓ 명령                         │
실제 세계 시뮬레이션 ◀─────────────┘

적 관측 → 적 지식 → 공격 계획 → 실제 세계 시뮬레이션

표현 계층은 각 계층의 공개 읽기 상태와 사건만 소비한다.
```

### 콘텐츠 정의

장비, 위협, 센서, 무기, 시설, 시나리오와 밸런스 값을 제공한다. 런타임 상태를 콘텐츠 resource에 기록하지 않는다.

모든 `DefenseDefinition`은 줄바꿈을 포함한 `purchase_tooltip`을 소유한다. HUD는 이를 자산 구매 `Button.tooltip_text`에 그대로 연결해 첫 줄의 역할과 둘째 줄의 운용 조건을 콘텐츠별로 관리한다. 지원 자산의 표시 이름은 `통합 지원기지`이며 scene은 보급 컨테이너와 정비동 외에 발전기와 변압 설비를 함께 포함한다.

### 세션·시나리오·경제

한 판의 단계, 예산, 해금, 통계, 게임오버, 저장과 공격 강도를 소유한다.

`ObjectiveDefinition`은 도시 기능의 최대치와 함께 1회 복구 비용과 회복량을 정의한다. HUD의 `도시 상태` 메뉴 버튼은 현재 값과 최대값을 항상 보여준다. 바로 아래 panel은 `도시 기반시설` 제목과 현재 상태를 먼저 보여주고, 공통 action row의 좌측에는 `피해 복구`, 우측에는 회복량과 비용을 정렬한다. 복구 행은 최대 상태, 예산 부족 또는 게임오버일 때 비활성화된다. 요청은 `AirscainMain`이 `GameSession.try_spend()`와 `ProtectedObjective.restore_integrity()`를 순서대로 호출해 처리하므로 준비와 전투 단계 모두에서 같은 즉시 교환 규칙을 사용한다.

HUD 상단 메뉴는 읽기 전용 `예산`, 구매 목록을 여는 `방공 자산`, 복구 항목을 여는 `도시 상태`로 책임을 분리한다. 정적 상태 Label에는 메뉴 화살표 너비에 상응하는 최소 폭을 줘 연속된 항목의 시각 중심을 맞춘다. context panel은 해당 버튼 아래에 배치하고 하나를 열면 나머지를 닫는다. 방공 자산과 도시 상태 panel은 같은 폭, header, separator와 action row 스타일을 사용한다. 샌드박스 전용 위협 선택은 별도 `위협 투입` context panel을 사용한다. 메뉴 항목 선택, 바깥쪽 좌클릭과 `ui_cancel` 입력은 열린 panel을 닫는다.

### 실제 세계 시뮬레이션

물리적 객체의 실제 위치, 운동, 소속, 임무, 피해, 탄약과 가동상태를 소유한다.

### 플레이어 지식

센서 관측, 항적, 추적 품질, 분류와 소속 판단을 소유한다. 실제 세계의 숨은 타입과 임무를 직접 참조하지 않는다.

### 지휘통제와 교전

각 방어체계가 접근 가능한 항적과 교전규칙을 이용해 표적과 무기를 선택한다.

### 적 지식과 공격계획

적이 관측한 제한된 정보와 과거 결과를 바탕으로 다음 공격 구성을 만든다. 실제 플레이어 자산 상태를 직접 읽지 않는다.

### 표현

메인 메뉴는 `MenuBackdrop`의 독립 `SubViewport`와 World3D에서 고정 seed의 방공 시연을 렌더한다. `MenuDefenseDemo` 자식 컨트롤러가 분리된 샌드박스 인스턴스의 실제 센서·C2·무장 tick을 구동한다. 탐색 레이더·지휘통제소·중/단거리 포대·기관포·지원기지를 도시 동쪽 가장자리에 정상 배치 검증으로 구성하고 약한 기본 UAV를 16초 간격, 최대 2개까지 투입한다. 무장은 도시 가까이에서 진입 회랑을 중첩 방어해 적기가 화면 안으로 접근한 뒤 요격되도록 하며 C2와 지역 지원 범위도 연결한다. 위협은 실제 시작 위치를 확정한 후 이동·임무 방향을 초기화한다. 예비탄·시설은 시연에서만 자동 유지하고, 도시 피격 시에는 피해 연기를 12초간 유지한 뒤 도시를 복구한다. 무작위 공격 확대, 전술 UI, 카메라 입력과 전투음은 끈다. App Shell의 플레이어 gameplay 참조·저장·시작 seed와는 분리하며 메뉴가 숨겨지면 viewport와 전체 시연 처리 모두 중단한다. UI는 해안 도시 전경 위에 좌측 명암 그라데이션과 모드 선택을 겹치며 배경 시연을 설명하는 별도 문구는 표시하지 않는다.

시설 세부 형상은 해당 콘텐츠 scene의 자식 스크립트에서 구성하며, `ModelGeometry`는 재질·상자·지지대·단면 동체·익면 생성만 제공한다. 센서의 모듈과 후면 프레임은 기존 회전 안테나에 연결되고, UAV와 타격기의 형상은 공통 비행·임무 코드와 분리된다. 레이저의 중심광 바깥에는 시선 방향에 맞춘 Gaussian ribbon halo를 사용하며 표적에는 따뜻한 가열 섬광과 국소 광원을 배치한다. `FieldPulse`는 각 인스턴스 재질을 별도로 소유해 HPM 효과를 시간 기반으로 팽창·감쇠하고, 종료 타이머의 과거 callback 없이 재사용한다. 장비의 표현 축척이 실제 효과 반경에 중복 적용되지 않도록 월드 basis로 크기를 설정한다. 에너지 효과 shader도 `CombatVfxWarmup`에서 최초 교전 전에 렌더한다.

지형 재질은 로컬 지형 법선으로 사면을 계산하고 저주파 색상 변화·절제된 등고선을 사용한다. 수면은 생성된 높이장의 float texture를 읽어 얕은 바다와 해안 포말을 표현하므로 depth texture나 플랫폼별 렌더 분기가 필요 없다. `LandscapeDetails`는 독립 seed RNG와 재질별 MultiMesh로 비전술 식생·암석·도로 디테일·차량·출입구를 생성하며 게임 판정에 참여하지 않는다. 건물 창문은 층별 창문 단위의 MultiMesh로 표현한다. 이 표현 개선은 기존 seed의 지표 높이·도시 배치 생성 함수를 유지해 이전 저장의 자산 위치와 충돌 판정을 보존한다.

3D 모델, VFX, 사운드, 항적 표식, 오버레이와 제품 UI를 담당한다. 게임 상태의 소유자가 아니다.

수면의 색과 미세 법선은 회전·왜곡한 두 규모의 비주기 value noise로 계산해 교차 정현파의 격자 반복을 피한다. 가로 디테일의 변환은 `회전 × 로컬 크기` 순서로 구성해 차량의 긴 축과 횡단보도 줄무늬가 도로 방향을 따른다.

## 5. 주요 모듈

모듈 경계는 다음 책임을 기준으로 유지한다. 실제 디렉터리와 파일 수는 기능 규모에 맞춘다.

| 모듈 | 책임 |
|---|---|
| App Shell | 메인 메뉴, 모드 진입, Esc 메뉴와 gameplay scene 생명주기 |
| Session | 게임 단계, 시간, 예산, 통계, 게임오버와 저장 진입점 |
| Training | 훈련 단계, 단계별 조건·안내와 훈련 표적 준비 |
| Scenario / Content | 사용할 전장, 자산, 위협과 밸런스 정의 |
| World | 절차적 지형, 도시, 공간 질의와 객체 생명주기 |
| Sensing | 센서 탐색, 시야 판정과 관측 생성 |
| Tracking | 관측 결합, 항적 생명주기, 추적 품질과 분류 |
| C2 | 항적 공유, 연결 상태와 장비별 정보 가용성 |
| Defense | 방어체계, 교전 판단과 구체 무기 운용 |
| Threat | 위협 이동, 임무, 대응책과 결과 처리 |
| Raid Director | 공격 강도, 적 지식과 공격 패키지 생성 |
| Support | 탄약, 전력, 재보급, 수리와 가동상태 |
| Presentation | 3D 표현, VFX, 사운드, 카메라와 UI |
| Persistence | 런타임 상태의 저장·복원과 버전 관리 |

모듈 간 직접 참조는 최소화한다. 서로 다른 모듈의 내부 node tree를 탐색해 상태를 가져오기보다 명시적인 참조, 읽기 모델, 명령과 signal을 사용한다.

gameplay scene root는 모듈 참조를 조립하고 상위 사건 흐름을 연결한다. 모드 전용 상태 머신은 root에 두지 않는다. 훈련 진행은 `TrainingController`가 소유하며 배치·선택·교전·지원 사건을 입력받아 단계와 안내를 갱신하고, 공통 선택 상태 변경이 필요하면 signal로 scene root에 요청한다.

훈련은 실습용 포대·고고도 센서·에너지 무기 참조를 보존해 다른 자산의 조작으로 완료되지 않게 한다. `SupportManager.task_completed`와 `RelocationManager.relocation_started/relocation_completed`를 통해 요청·완료를 분리하고 작업 구간만 자동 재생한다. C2 경로가 연결되어야 방어를 시작하며, 지원기지가 실습 포대를 지원할 수 있어야 보급 단계로 진입한다. 고급 실습 진입 시 훈련에서만 단계 3 장비를 해금하고, 실제 게임과 같은 예산·지원·피해·전력 판정을 사용한다.

배치 미리보기는 선택한 콘텐츠 scene을 갱신이 중단된 상태로 잠시 생성해 초기화된 모델의 가시 mesh와 누적 transform만 복사한다. 즉시 원본 노드를 제거하므로 미리보기에 자산 로직·광원·파티클·게임 등록이 남지 않는다. 복사한 mesh는 공용 배치 가능/불가 재질과 그림자 없는 표현을 사용하고 기존 범위·연결선·전력 안내와 조합된다.

## 6. Scene과 컴포넌트 설계

하나의 배치 자산이나 위협은 독립적으로 생성·제거할 수 있는 scene으로 구성한다.

scene root는 객체의 정체성과 생명주기를 담당하고, 필요한 능력은 조합 가능한 컴포넌트로 구성한다.

대표적인 능력 단위:

| 능력 | 책임 |
|---|---|
| Integrity | 체력, 성능저하, 기능정지와 파괴 상태 |
| Signature | 센서가 관측할 수 있는 레이더·열·시각 특성 |
| Sensor | 탐색주기, 시야와 관측 생성 |
| C2 Endpoint | 로컬 항적과 공유 항적의 수신·전달 가능 상태 |
| Movement | 속도, 선회, 고도와 경로를 포함한 실제 운동 |
| Mission | 위협의 목표, 성공 조건, 철수와 결과 |
| Engagement | 이용 가능한 항적 평가와 교전 요청 |
| Weapon | 미사일, 기관포, 레이저 등 구체 공격 방식 |
| Magazine / Energy | 탄약, 충전, 냉각과 재보급 상태 |
| Support Consumer | 재보급·수리·전력 능력의 요구량과 상태 |

모든 객체가 이 능력을 전부 가질 필요는 없다. 하나의 거대한 base class에 선택적 필드를 모으지 않는다.

컴포넌트는 가능한 한 자신의 상태만 소유한다. 여러 능력을 조정하는 규칙은 해당 객체의 controller 또는 상위 시스템이 담당한다.

공통 배치·UI·오버레이·지원 시스템은 구체 자산 클래스를 판별하지 않고 `DefenseDefinition`과 `DefenseUnit`의 capability query를 사용한다. Definition은 카탈로그 그룹, 전술 범위 종류·반경, 배치 시 C2·지역 지원·전력 정보를 제공하고 runtime은 교전 제어, 탄종 선택, 재보급, 지원 처리와 전력 공급 능력을 제공한다. 지원하지 않는 능력은 중립값을 반환한다. 새 자산 종류는 자신의 Definition과 runtime에서 필요한 capability만 재정의하며 공통 소비자에 타입 분기를 추가하지 않는다.

## 7. 콘텐츠 정의와 런타임 상태

콘텐츠 정의에는 안정적인 ID, 표시 정보, scene 참조와 해당 콘텐츠가 사용하는 조정값을 둔다.

주요 정의 범주:

- 시나리오와 전장 생성 설정
- 보호 목표와 핵심 시설
- 센서와 지휘통제 장비
- 방어체계와 무기·탄약
- 위협과 이동·임무 유형
- 지원시설과 운용 능력
- 공격 패키지와 난이도 설정

공통 정의에는 생성, 선택과 공통 UI에 필요한 값만 둔다. 구체 콘텐츠 전용 값은 해당 정의에 둔다.

예를 들어 미사일 가속과 유도값을 모든 방어체계 정의에 넣거나, 레이저 전력값을 모든 무기 정의에 optional 필드로 넣지 않는다.

런타임 상태와 콘텐츠 정의는 분리한다.

```text
Definition / Resource
→ 변경하지 않는 콘텐츠와 밸런스

Runtime State
→ 현재 체력, 위치, 탄약, cooldown, 항적과 임무 상태
```

같은 resource를 사용하는 여러 객체가 서로의 런타임 상태를 공유해서는 안 된다.

## 8. 상태 변경과 사건 흐름

명령은 상태 소유자에게 전달하고, 소유자가 검증 후 상태를 변경한다.

대표 흐름:

```text
플레이어 입력
→ 구매·배치 명령
→ 비용과 배치 조건 검증
→ 상태 변경
→ 성공 또는 거절 사건
→ UI와 VFX 갱신
```

```text
무기 교전
→ 발사 가능 여부 검증
→ 탄약·채널 예약
→ 무기 작동
→ 충돌·효과 판정
→ 피해 또는 상태효과
→ 위협 결과 확정
→ 보상·통계 갱신
→ VFX와 사운드
```

signal은 변화 통지와 느슨한 결합에 사용한다. 중요한 상태 변경 자체를 여러 signal listener에 분산하지 않는다.

동일 위협의 무력화, 임무 성공, 보상과 도시 피해는 각각 정확히 한 번만 확정한다.

## 9. 시뮬레이션 시간과 난수

물리적 이동, 유도와 충돌은 Godot의 고정 physics tick을 기준으로 처리한다. 기본 목표는 `60 Hz`다.

모든 시스템을 매 physics tick에 실행할 필요는 없다.

- 이동, 고속 유도와 충돌: physics tick
- 센서 scan: 센서별 scan 주기
- 표적 선택과 항공 AI: 더 낮은 주기 또는 상태 변화 시
- 공격 계획과 지원 배정: 낮은 주기 또는 사건 기반
- 네트워크와 지원 연결 재평가: topology가 변할 때

렌더링은 시뮬레이션 상태를 표현하며 필요하면 위치를 보간한다.

난수는 최소한 다음 흐름을 분리한다.

- 전장 생성
- 공격 패키지와 spawn
- 개별 위협 행동
- 탐지·피해 등 확률 판정
- 시각효과

같은 전장 seed는 전장 구성을 재현해야 한다. 전체 게임을 비트 단위로 완전히 결정론적으로 만들 필요는 없지만, gameplay 난수가 시각효과의 난수 소비 때문에 바뀌어서는 안 된다.

## 10. 좌표, 지형과 공간 질의

월드 좌표는 미터 단위로 해석한다. 장비 크기, 속도, 고도, 사거리와 VFX 크기는 같은 상대 스케일을 사용한다.

절차 지형 material은 vertex 고도를 전달해 고도별 색, 일정 간격의 등고선과 법선 기반 사면 명암을 합성한다. 이 표현은 배치·차폐에 사용하는 높이장 자체를 변경하지 않는다.

절차적 전장은 하나의 논리 height field에서 다음을 함께 만든다.

- terrain mesh
- terrain collision
- 배치 높이와 경사 query
- 저고도 이동과 시야 판정에 필요한 지형 높이

기본 지형 함수는 다음처럼 저주파 형태와 세부 요철을 분리한다.

```text
height(x, z) = macro_shape + detail_noise
```

섬의 해안 mask는 단순 방사 거리가 아니라 seed에서 유도한 3중·5중 방향 굴곡과 저주파 noise로 방향별 반경을 바꾼다. 지도 가장자리에는 별도 해수 감쇠를 적용해 가장 긴 곶도 전장 경계를 넘지 않게 한다. 시가지 필지는 중앙 업무지구를 항상 포함하되 seed에서 유도한 방향별 경계 굴곡 안에서만 후보가 되며, 외곽 후보는 해수면 고도와 경사 제한을 통과해야 한다. 필지를 확정한 뒤 활성 영역과 지형 메시 보간에 참여하는 주변 정점을 일정 고도로 평탄화하고, 그 바깥은 거리 가중치로 원래 지형에 부드럽게 잇는다. 각 활성 필지에만 아스팔트 도로 tile과 보도 블록을 만들고 인접 필지 사이에만 중앙선을 이어, 하나의 정사각 아스팔트 판이 생기지 않게 한다. 건물 크기와 높이는 중심 가중치로 조절하고 외곽 필지에는 여러 저층 동을 배치하며, 빈 필지는 공원이나 주차장으로 채운다. `Battlefield`는 같은 건물 transform과 기단·지붕 여유를 2D 점유 사각형으로 캐시해 장비 원형 footprint와 교차 판정한다. 중앙 시민 건물은 실제 `CivicHall` mesh 크기에서 점유면을 계산한다. 따라서 기존 도시 반경 금지는 없고 실제 건물 사이의 빈 지면은 나머지 지형·경사 조건에 따라 배치할 수 있다. 방어 자산과 위협의 root 시각 축척은 `0.9`를 사용하지만 배치 footprint, 센서·무장 거리와 비행 좌표는 바꾸지 않는다.

공간 질의는 우선 Godot physics의 ray, shape와 area query를 사용한다. 실제 프로파일링에서 모든 객체 전수조사가 병목으로 확인되면 spatial hash, grid 또는 별도 인덱스를 도입한다.

반복되는 층별 창문 띠는 하나의 `MultiMeshInstance3D`로 묶고, 기단·옥상 캡·펜트하우스·HVAC처럼 실루엣을 바꾸는 요소만 독립 node로 유지한다. 보호 목표인 시민 건물과 선택 가능한 객체도 독립 node다. 옥상 배치 가능 위치는 데이터와 충돌면을 상시 유지하되 시각 링은 호환 장비의 배치·재배치 중에만 표시한다.

## 11. 센서와 관측 모델

센서는 실제 객체를 직접 항적으로 만들지 않고 **관측값**을 생성한다.

관측에는 최소한 다음 정보가 필요하다.

- 센서 식별자와 시각
- 관측 위치 또는 거리·방위 정보
- 측정 품질과 불확실성
- 관측된 signature 또는 분류 단서

### 시야

지형과 주요 차폐물에 가려지면 관측할 수 없다. 기본 구현은 raycast 또는 제한된 수의 지형 sample을 사용한다. 모든 도시 건물의 정밀 전파 차폐를 계산할 필요는 없다.

각 센서 definition은 지형 기준 최소·최대 탐지고도를 갖고 거리·가시선 판정 전에 고도 envelope를 검사한다. 기본 탐색 레이더와 고고도 추적 레이더는 겹치지만 서로 다른 고도대와 탐지거리를 담당한다.

### 정규화된 신호 품질

실제 레이더 방정식 대신 조정 가능한 정규화 모델을 사용한다.

```text
signal_quality =
    sensor_quality
    × signature_factor
    × aspect_factor
    × environment_factor
    × ew_factor
    × range_factor
    × line_of_sight
```

```text
range_factor = 1 / (1 + (distance / reference_range) ^ exponent)
```

- 각 factor는 `0..1` 범위로 정규화한다.
- `line_of_sight`는 기본적으로 `0` 또는 `1`이다.
- `exponent`와 기준 거리는 센서 콘텐츠가 조정한다.
- 공개 제원을 모사하기보다 센서별 강점과 약점을 만드는 것이 목적이다.

### 탐지 증거

한 번의 미약한 관측이 즉시 안정된 항적이 되지 않도록 증거를 누적할 수 있다.

```text
detection_evidence += signal_quality × observed_time
detection_evidence -= decay_rate × unobserved_time
```

잠정 항적과 확인 항적의 임계값은 콘텐츠나 시나리오가 조정한다.

## 12. 항적 모델

항적은 실제 객체와 별개의 플레이어 지식 객체다.

최소 상태:

- 안정적인 항적 ID
- 추정 위치와 속도
- 마지막 관측시각
- 추적 품질과 위치 불확실성
- 분류 점수와 확신도
- 소속 판단과 확신도
- 관측에 기여한 센서
- 생명주기 상태

### 생명주기

```text
TENTATIVE → CONFIRMED → COASTING → LOST
```

관측이 없을 때는 마지막 속도로 짧게 예측한다.

```text
predicted_position = position + velocity × dt
```

새 관측은 예측 위치와 측정 품질에 따라 점진적으로 반영한다.

```text
position = lerp(predicted_position, measured_position, position_gain)
velocity = lerp(previous_velocity, measured_velocity, velocity_gain)
```

gain은 측정 품질과 현재 불확실성에 따라 달라진다. 관측 간 위치 차이로 계산한 속도와 갱신된 추정 속도는 공통 결합 정책의 최대 속도로 제한해, 밀집 표적의 순간적인 오결합이 항적을 전장 밖으로 발산시키지 않게 한다. 현재 simulation time까지 이미 예측된 위치에는 관측 시각이 앞선 차이만 추가 예측한다. 처음부터 Kalman Filter를 필수로 하지 않는다. 더 정교한 필터가 필요해져도 항적의 공개 상태와 생명주기는 유지한다.

### 관측 연결

새 관측은 예측 위치 주변의 제한된 gate 안에 있는 항적 후보와 연결한다. 첫 구현은 안정적인 nearest-neighbor 방식으로 충분하며, 밀집 표적에서 실제 문제가 확인되면 더 정교한 data association으로 교체한다.

### 추적 품질

관측이 들어오면 증가하고, 관측이 끊기면 시간에 따라 감소한다. 불확실성은 반대로 증가한다. UI와 교전 판단은 같은 추적 품질을 사용한다.

### 분류와 소속

분류와 소속 판단은 위치 추적과 분리한다.

```text
class_score[type] += feature_match × observation_quality
affiliation_score[state] += evidence × source_reliability
```

점수를 정규화해 확신도로 사용한다. 내부 알고리즘은 단순 가중치부터 시작할 수 있으며 실제 Bayesian 추론을 요구하지 않는다.

## 13. 지휘통제 모델

C2는 센서와 방어체계 사이의 **정보 접근 가능성**을 결정하는 graph로 표현한다.

node는 센서, 지휘소, 중계시설과 방어체계가 될 수 있고 link는 현재 연결 상태, 품질과 선택적 지연을 가진다.

```text
available_tracks(node)
=
local_tracks
∪ tracks reachable through active C2 links
```

경로 품질과 지연을 사용할 경우 단순하게 집계한다.

```text
path_quality = product(link_quality)
path_latency = sum(link_latency)
```

첫 구현은 연결 여부만 사용할 수 있다. 품질과 지연은 전자전 또는 대규모 네트워크가 실제 gameplay에 필요해질 때 활성화한다.

항적 갱신을 개별 패킷으로 시뮬레이션하지 않는다. 네트워크 변화가 발생하면 연결성과 장비별 사용 가능 항적을 재평가한다.

방어체계는 로컬 센서와 C2를 통해 전달받은 항적만 교전에 사용한다.

배치 미리보기는 실제 endpoint와 같은 거리, 가동상태와 재밍 판정을 후보 definition에 적용한다. 후보에서 직접 연결되는 endpoint들의 기존 연결 성분을 합쳐 센서, 지휘와 방어 역할 충족 여부를 계산한다. 직접 연결선은 구성 완성 여부와 관계없이 C2를 뜻하는 청색으로 유지하고, 후보의 C2 범위 원만 완성 시 청색, 불완전 시 주황색으로 표시한다.

## 14. 교전과 Doctrine

교전 모듈은 다음 순서로 동작한다.

```text
사용 가능한 항적
→ 무기로 처리 가능한 후보
→ 위협도와 비용 평가
→ 교전 예약
→ 구체 무기에 발사 요청
```

### 위협 긴급도

실제 위협의 숨은 목표가 아니라 항적에서 추정한 예상 탄착과 시간을 사용한다.

```text
urgency =
    protected_value
    × estimated_impact_probability
    / max(time_to_impact, minimum_time)
```

### 교전 점수

```text
engagement_score =
    urgency
    × weapon_match
    × track_quality
    × doctrine_weight
    - resource_penalty
```

- `weapon_match`는 표적 종류, 거리, 고도와 무기 특성의 적합도다.
- `resource_penalty`는 고가 탄약, 예비탄 부족, 낮은 명중 예상 등을 반영한다.
- 모든 값은 절대적인 실제 확률이 아니라 비교 가능한 정규화 값이다.

교전 조정은 Definition의 공통 예약 방식으로 요격체와 근접 화력 지원을 구분한다. 미사일 포대는 실제 발사한 요격탄마다 예약 한 건을 만들고, 종료하거나 재표적화한 요격탄의 예약 한 건만 해제한다. 동일 항적의 요격체 예약 상한은 2발이며 기관포·레이저·HPM의 조준 배정은 이 슬롯을 소비하지 않는다. 근접방어는 자산별 한 항적에 0.5초 배정을 갱신하며, 다른 무기가 교전 중이라는 이유로 조준이나 사격을 금지하지 않는다. 표적 점수는 공개 항적의 품질·무기 적합도·도시까지 거리·도시 방향 접근 속도를 반영하고, 다른 자산이 담당하는 표적에는 완만한 감점을 적용해 비슷한 위협을 분담한다. 현재 배정은 가산점을 받아 불필요한 조준 전환을 줄인다. 단독·긴급 표적에는 집중 사격할 수 있고 플레이어의 우선 표적 지정은 유지한다. 사거리·C2·교전규칙·조준 정렬·탄약·충전·과열 조건은 그대로 적용하며 발사 자원이 없거나 유효 표적이 사라지면 배정을 해제한다.

직접 명령은 자동 판단을 영구적으로 대체하지 않는다. 우선표적, 특정 무기 할당과 사격중지 같은 제한된 override로 처리한다.

## 15. 무기 모델

무기는 공통 교전 요청을 받지만 내부 작동 방식은 각 무기 유형이 소유한다. 모든 공격을 하나의 범용 projectile 계층에 억지로 맞추지 않는다.

### 유도 요격체

유도 입력은 항적의 추정 상태를 사용한다. 빠른 표적은 추정 위치와 속도의 정속 모델로 제한된 시간의 선행점을 계산해 추적 지연을 줄인다. 속도, 최대 횡가속도와 비행시간을 제한한다. 미사일 포대는 발사 시점마다 항적·탄종·교전 예약·채널을 다시 평가하고 준비탄 한 발만 소비해 서로 다른 발사 위치와 탐색기 난수열을 가진 실제 요격체를 발사한다.

직사 회전식 무기는 공통 2축 조준 계산으로 yaw와 pitch를 각각 제한속도로 갱신하고 두 축이 허용각 안에 들어온 뒤 발사한다. 미사일 포대는 최소 상향 발사각 20도를 보장하며, 실제 발사관이 이 각도에 도달하기 전에는 넓은 발사 구역 안이어도 발사를 보류한다. 고각 표적에는 기존 조준을 유지하고 별도 지형 검사나 유도 변경은 하지 않는다. 최소 앙각을 만족하면 `LaunchPoint`의 물리적 전방축과 표적 방향이 30도 발사 구역 안이면 포탑을 더 돌리지 않고 그 전방축으로 사출한다. 구역 밖일 때만 공통 2축 조준기로 구역 경계까지 회전한다. 5도 넘게 비정렬 사출된 요격체는 첫 0.55초 동안 유도 선회율을 28%에서 100%로 높여 초기 경로가 즉시 표적 직선으로 꺾이지 않게 한다. 요격체 종료는 성공 명중과 유도 상실·시간 초과·대응책 기만을 구분해 표현 계층에 전달한다.

발사 랙은 scene의 `MuzzleCaps` 수와 같은 준비탄을 가진다. 교전 가능한 항적이 있는 동안 중거리 0.56초, 단거리 0.4초, 장거리 0.7초 간격으로 준비탄을 한 발씩 발사한다. 한 항적에는 전역 할당 상한까지만 발사하고 다음 발사 시점에는 다른 항적을 포함해 우선순위를 다시 평가한다. 해당 탄종의 준비탄이 소진되면 중거리 9초, 단거리 6초, 장거리 12~14초 동안 탄창 전체를 재장전한다. 발사된 셀의 cap은 숨기고 재장전 완료 시 복원한다. 탄종별 준비탄·예비탄과 재장전 잔여시간은 선택 상세에서만 표시하고 월드 상태 표식에는 중복 표시하지 않는다.

중·장거리 요격체에는 단순화한 proportional navigation을 기본 유도 방식으로 사용할 수 있다.

`MissileBattery`의 고갈 capability는 모든 탄창을 검사한다. 전체 고갈은 `탄약 고갈`, 일부만 고갈이면 `일부 탄종 고갈`을 표시하며 각 탄종의 수량은 상세 패널에 둔다. 자동 모드의 최후 고가탄 보존은 `MissileMunitionDefinition.is_preferred()`가 아닌 표적에만 적용한다. 우선표적과 명시적 탄종 모드는 보존을 해제하지만 다른 교전 조건은 그대로 유지한다. 탄종 적합도가 0인 경우에는 후보에서 제외한다.

```text
lateral_acceleration =
    navigation_constant
    × closing_speed
    × line_of_sight_rate
```

결과는 요격체의 최대 횡가속도로 제한한다. 콘텐츠에 따라 boost, midcourse와 terminal phase를 둘 수 있지만 모든 미사일에 같은 phase를 강제하지 않는다.

미사일 포대 definition은 지형 기준 최소·최대 교전고도를 가지며 항적 선택 단계에서 사거리와 함께 검사한다. 단거리 0–180m, 중거리 0–450m, 장거리 100–1500m를 기본 계층으로 사용한다.

포대 계층은 definition마다 별도 scene을 연결해 외형도 분리한다. 단거리는 IRIS-T SLS 계열에서 가져온 소형 4연장·고각 실루엣, 중거리는 NASAMS의 6발 모듈식 2×3 랙, 장거리는 Patriot 계열의 대형 4발 2×2 캐니스터와 넓은 차대 비례를 로우폴리로 단순화한다. 공통 스크립트가 요구하는 `Turret/Elevation/Launcher/LaunchPoint` 계층은 유지한다.

고속 객체의 명중과 근접신관은 한 tick의 이전 위치와 현재 위치를 잇는 swept query로 판정한다. discrete overlap만 사용해 표적을 통과하지 않게 한다.

### 기관포

시한 만료(`timeout`)로 자폭한 기관포 탄은 `CombatAudio`의 `GunAirburstAudio` 한 개로 모아 재생한다. 포대 수·탄수만큼 소리를 중첩하지 않고, 제공된 `gun_self_destruction_1.ogg`의 앞뒤 무음을 포함한 전체 원본을 반복한다. 명중 근접신관·지면 충돌은 이 자폭음의 시작 조건이 아니다. 자폭 간격 0.25초는 같은 흐름으로 유지하고 더 이상 자폭이 없으면 0.3초 페이드아웃한다. 페이드 중 자폭이 재개되면 재생 위치를 유지한 채 볼륨을 회복한다. 실제 탄 발사와 독립적이므로 사격 중지 후 남은 탄의 자폭도 반영하며, 일시정지·메뉴 음소거를 따르고 성공한 저장 복원 시 이전 작전의 재생을 정리한다.

기관포 사격음은 `GunAudio`가 시작과 루프를 이어 붙인 공유 `gun_sustain.ogg`를 재생하며, 처음 25,216개 프레임(44,100Hz)의 시작 구간 다음부터 네이티브 루프를 반복한다. 종료음은 제공된 원본 Ogg를 별도 플레이어로 0.06초 크로스페이드한다. 원본 파일은 보존하며 WAV 배포 자산은 사용하지 않는다. 웹에서는 이 두 스트림과 공통 자폭 루프를 기존 전투음과 함께 시작 시 Sample로 사전 등록한다(총 24개). 재생마다 스트림을 복제하거나 WASM 스트리밍 믹서에서 디코딩하지 않는다. 네이티브 실행은 Stream 경로를 사용한다.

`CombatAudio`는 실제 들리는 대표 기관포를 최대 4개로 제한한다. 현재 사격 중인 대표를 유지하고 빈자리에 다른 사격 포대를 배정하며, 종료 잔향보다 진행 중 사격을 우선한다. 나머지 포대는 재생 위치와 사격 상태만 추적하고 실제 오디오는 재생하지 않는다. 대표 교체 시 경과 위치에서 이어 재생해 시작음을 반복하지 않으며 짧은 페이드 동안만 이전 음성이 겹친다. 대표 음성들의 선형 gain 합은 최대 0.65, 개별 gain은 최대 0.25로 제한해 다중 포대 합산 포화를 줄인다. 탄도·명중·발사 횟수는 제한하지 않는다.

실제 개별 탄의 발사 신호만 재생을 갱신하며 0.12초의 짧은 사격 간격은 하나의 연사로 유지한다. 같은 프레임에 수신한 탄은 프레임 지연만으로 종료하지 않는다. 사격 중단 시 종료음의 잔향을 재생하고, 잔향 중 재사격하면 시작음으로 크로스페이드한다. 작전 일시정지 때 재생 위치를 보존하고 메뉴 시연에서는 전투음 설정을 따라 재생하지 않는다. 실제/가상 음성의 시간 갱신은 작전 일시정지 상태를 따르며 플레이어의 pause 속성은 상태가 바뀔 때만 설정한다. 매 프레임 동일한 resume을 호출해 웹 Sample 소스를 반복 생성하지 않는다. 표적 변경·burst 예약은 소리를 재시작하지 않으며 비행 중인 탄의 상태와 오디오 재생 상태는 분리한다.

모델은 [Raytheon의 Phalanx 공개 사진](https://www.rtx.com/en/raytheon/what-we-do/sea/phalanx-close-in-weapon-system)을 참고한 로우폴리 CIWS 실루엣이다. 밝은 원통형 레이더 돔과 둥근 상부, 하부 탄약 드럼, 양측 포 지지대, 6연장 회전 총열과 측면 광학 추적기를 scene에 구성한다. `Turret/Elevation/Muzzle`의 기존 발사 원점과 조준 축을 보존하며 총열 묶음은 그 축 주위로만 회전한다. 실제 발사 신호로 회전하고 사격이 멈추면 감속한다. 광학·레이더 외형은 새 탐지 능력을 부여하지 않으며 게임의 기존 센서·C2 요구를 유지한다.

기관포는 사거리 260m에서 0.28초 간격으로 12발씩 사격하며, 한 burst 안에서는 초당 45발·620m/s의 발사 간격과 탄속을 사용한다. 기존 탄약·경제 단위는 burst 하나이며 총 피해량 24를 12발에 나눈다. `CloseInGunDefinition`이 탄수·발사율·속도·신관 설정을 소유하고, 포대의 `GunfireRuntime` 자식이 발사 대기와 비행탄을 수치 상태로 묶어서 처리한다. 독립 PhysicsBody나 Mesh 노드를 탄마다 생성하지 않는다.

포대는 공개 항적의 추정 속도와 중력 낙하를 고려해 선행 조준한다. 항적 품질·명중 성능·표적 상성과 거리는 발사 시 각도 분산에 반영되며 발사 후 유도는 없다. 실제 위협의 이동과 탄의 이동을 상대 선분으로 검사해 3.5m 근접신관을 판정한다. 포구 근처 0.04초는 신관 안전시간이며, 빗나간 탄은 조준 위치를 지나 약 1.05초(탄별 ±10%) 수명 끝에 자폭한다. 지형·건물과 먼저 만나면 해당 접점에서 종료한다. 시각 폭발 자체는 추가 피해를 반복하지 않는다.

예광 core·halo와 공중폭발 섬광·연기는 각각 고정 160개 `MultiMesh` 버퍼를 사용한다. 탄 간격은 예광 길이보다 길며 포구 섬광·광원은 실제 탄 발사에 맞춰 점멸한다. 앱 예열에도 같은 렌더 경로를 포함한다. 시뮬레이션 tick만 비행을 진행하고 0.02초 이하로 내부 분할하므로 정지·배속을 따르며, 사격중지·재배치·포대 무력화는 발사 대기 탄만 취소하고 이미 나간 탄은 계속 비행한다. 발사 대기 시간·탄의 위치/속도·신관·피해 상태는 포대 콘텐츠와 함께 저장하고, 순수 폭발 잔상은 저장하지 않는다.

### 레이저

레이저는 line of sight가 유지되는 동안 열적 dose를 누적한다.

```text
effective_power =
    rated_power
    × track_quality
    × atmosphere_factor
    × range_factor
```

```text
thermal_dose += effective_power × dt
thermal_dose -= cooling_rate × interrupted_time
```

임계 dose에 도달하면 손상 또는 무력화한다.

### 고출력 마이크로파

HPM은 범위와 방향 안의 전자표적에 상태효과를 누적한다.

표적별 `electronic_vulnerability`가 결합 강도를 정의한다. 조류는 전자표적보다 낮은 값 `0.15`를 사용해 단일 펄스로 즉시 사라지지 않으며, 누적 피해로 무력화될 때는 폭발·연기 없이 현재 속도의 일부를 유지한 작은 낙하체로 전환한다.

```text
effect =
    emitted_power
    × target_susceptibility
    × range_factor
    × direction_factor
```

결과는 일시적인 조종·센서 장애, 영구 기능저하 또는 추락이 될 수 있다.

### 요격드론

요격드론은 출격, 순찰·요격, 복귀와 재충전 상태를 가진 독립 물리 객체다. 항적 속도로 선행점을 계산해 이동 표적을 추적하고, 타격 또는 체공시간 종료로 귀환을 시작할 때 교전 예약을 해제해 후속 출격을 막지 않는다. 재사용 가능성 대신 속도, 체공시간과 동시 출격 수의 제한을 가진다.

## 16. 위협 운동과 임무

위협은 이동 모델과 임무 모델을 조합한다.

대표 이동 모델:

- 일정 고도 또는 waypoint 기반 UAV
- 제한된 선회와 고도변화를 가진 항공기
- 지형 높이를 참고하는 저고도 순항체
- 중력과 초기조건을 사용하는 탄도체
- 목표를 향해 직접 접근하는 단순 발사체

비행체는 현재 속도를 한 tick에 목표 방향으로 즉시 회전시키지 않는다. 콘텐츠가 정의한 최대 선회율, 횡가속도와 상승·하강 속도로 제한한다.

공격 위협의 출발 반경은 이동 프로필이 전장 크기에 대한 배율로 정의한다. 일반 위협은 섬 바깥 바다에서 진입하고 탄도 위협은 더 먼 발사지점에서 출발한다. 비탄도 항공체의 순항·종말 안전고도는 지형과 해수면 중 높은 표면을 기준으로 하며, 타격 후 이탈 중에도 이 기준 아래로 내려가지 않는다. 임무별 종말고도와 종말 전환거리를 사용해 타격 항공기는 지상으로 충돌하지 않고 투하고도에서 무장을 분리한다.

순항체의 지형추종은 진행방향의 제한된 지형 sample에서 안전고도를 정하고 부드럽게 따라가면 충분하다. 종말거리에 한 번 진입하면 `terminal_committed`를 유지해 거리가 잠시 다시 벌어져도 순항 안전고도로 복귀하지 않는다. 지형추종체는 종말구간에서 선회율을 높이고 목표와 정렬되지 않았을 때 감속한다. 매 tick의 이전·현재 위치 구간에서 목표까지의 최근접점을 구해 `action_distance` 안을 통과하면 그 점에 위치를 고정한 뒤 충돌 임무를 적용하므로 4× 진행에서도 목표를 건너뛰지 않는다. 완전한 3D 공력과 최적 경로계획을 요구하지 않는다.

탄도체는 가속 상승, 중간비행과 재진입을 구분한다. 상승 구간은 수평 이동을 억제하고 빠르게 정점에 접근하며, 중간비행은 고도를 유지하고, 재진입은 목표 근처에서 하강률이 급격히 증가한다. 필요한 콘텐츠만 종말 조향을 추가한다.

임무 모델은 다음을 소유한다.

- 목표 선택
- 성공 조건
- 무장 투발
- 정찰 또는 방사 관측
- 전자전·기만 수행
- 철수 조건
- 임무 완료 효과

위협이 임무를 완료해도 항상 도시와 충돌하는 것은 아니다. 정찰 완료, 무장 투발, 방공망 방해와 성공적인 철수도 임무 결과가 될 수 있다. 정찰·전자전 효과를 유지하는 항공체는 순항 안전고도를 보존하고 수평 작전반경 안에서 목표 주변을 선회한다.

일반 항공 이동도 종말구간 밖에서는 현재 지형에 대한 최소 안전고도를 사후 보정한다. 장시간 체공 임무의 선회 반경은 임무 작용거리에서 직접 유도해 도시 중심 침범과 급격한 안쪽 회전을 피한다.

## 17. 피해와 상태효과

기본 피해는 다음 종류로 제한한다.

- 직접 피해
- 반경 피해
- 열적 피해
- 전자적 기능저하

반경 피해는 단순한 거리 감쇠를 사용한다.

```text
area_damage = max_damage × falloff(distance / radius)
```

`falloff`는 선형, smoothstep 또는 지수형 중 콘텐츠에 맞는 하나를 사용한다. 실제 파편 각각을 생성하지 않는다.

객체의 기본 상태는 integrity와 operational state로 표현한다.

```text
OPERATIONAL
→ DEGRADED
→ DISABLED
→ DESTROYED
```

부분손상이 gameplay에 명확한 차이를 만드는 복합 장비에만 제한된 subsystem 상태를 추가한다. 모든 객체에 동일한 부품 트리를 강제하지 않는다.

피해와 상태효과는 실제 세계 계층에서 처리하고, 항적은 센서가 관측할 수 있는 변화만 반영한다.

## 18. 탄약, 전력과 지원

탄약과 에너지는 장비별 런타임 상태다.

- 발사 시 탄약 또는 에너지 소비
- cooldown, 충전과 냉각
- 재보급·재정비 요청
- 지원 능력에 따른 완료시간

재보급과 수리는 queue로 관리할 수 있다.

```text
operation_duration =
    base_work
    / max(effective_support_capacity, minimum_capacity)
```

통합 지원기지는 수평거리 260m 안의 방공 자산에 재보급과 수리를 제공한다. 작업 요청과 진행 시 C2 연결은 요구하지 않으며, 대상은 범위 안에서 가장 가까운 가동 지원기지에 동적으로 배정된다. 각 기지는 자신의 동시 작업 수만큼 대기열을 처리하고 유효 처리량을 진행 작업에 나눈다. 대상이 범위를 벗어나거나 담당 기지가 기능 정지되면 다른 유효 기지가 없는 동안 작업은 대기한다. 시설 손상은 작업 범위가 아니라 처리량을 낮춘다.

`SupportManager`는 자산별 자동 재보급 활성 ID를 소유한다. 시뮬레이션 시간 기준 초당 한 번, ID 순으로 유효·가동 자산의 `combat_resource_low()`를 검사하고 기존 `request_resupply()`를 호출한다. 따라서 다중 탄종의 최저 예비탄 비율, 비용·범위·대기열·재배치 제한을 공통 capability와 요청 경로로 처리하며 중복 작업이나 중복 지출을 만들지 않는다. 선택 패널의 교전 설정에 `자동 재보급` CheckButton을 두며 부가 문구나 설명 툴팁을 붙이지 않는다. 기본 꺼짐이고 진행 중 작업을 취소하지 않는다. 지원 작업의 요청·완료 신호를 훈련 컨트롤러에 전달해 자동 요청도 보급 실습을 진행시킨다. 활성 ID 목록은 지원 작업과 함께 저장하며 복원 시 자동 결제하지 않는다.

자동 재보급을 켠 무장 자산의 상태 표시는 탄종/전체 고갈 경고 대신 실제 활성 작업에 대해 `재보급 중`, 자원 부족이나 지원 범위·대기열 등으로 시작하지 못한 경우 `재보급 대기`를 사용한다. 기능 정지·손상 표시는 우선하며 자동 재보급을 끄면 기존 고갈 경고로 돌아간다.

전력은 복잡한 송배전망 대신 가용 용량과 소비량으로 모델링한다.

```text
available_power = generation_capacity - committed_demand
```

우선순위가 높은 소비자부터 용량을 배정한다. 전력망 topology가 실제 gameplay에 필요해지는 시나리오가 생기기 전에는 발전소·변전소·장비 사이의 전력 흐름을 graph로 계산하지 않는다.

`PowerManager`는 가동 중인 에너지 소비 자산의 명목 수요 합계를 제공한다. 에너지 무기와 통합 지원기지 배치 미리보기는 후보 definition의 수요 또는 공급 용량을 더해 현재 상태와 배치 후 상태를 비교한다. 이 정보 panel은 후보의 화면 투영 위치 옆에 배치하고 viewport 안으로 제한한다. 전력은 거리나 담당 발전기가 없는 전역 capacity 모델이므로 자산 사이에 전력 연결선을 만들지 않는다. 설치된 에너지 무기의 선택 상세는 장비 수요, 총 공급량과 전체 공급 부족 여부를 `PowerManager.consumer_status()`로 표시한다.

`C2Overlay`는 C2와 지역 지원을 하나의 전술 관계 표시 경로에서 조합한다. 청색 C2선은 배치 후보에는 `C2Network.placement_preview()`의 직접 endpoint를, 설치 자산에는 `C2Network.active_links()` 중 선택 자산에 닿는 직접 link를 사용한다. 구성 완성 여부는 선 색이 아니라 C2 범위 원의 청색·주황 상태로만 구분한다. 녹색 지원선은 `SupportManager`의 동일한 거리 판정을 사용하며, 지원기지 후보·선택에는 범위 안의 지원 가능한 자산 전체를, 다른 후보·선택 자산에는 가장 가까운 가동 지원기지 하나를 연결한다. 따라서 같은 위치의 배치 미리보기와 설치 후 선택은 같은 연결 대상과 색을 유지한다. 전체 C2 overlay는 기존처럼 모든 C2 link만 표시하고 선택 자산의 지역 지원 관계와 섞어 전장 전체를 상시 표시하지 않는다.

배치 범위와 C2 범위의 `TorusMesh`는 원주 방향 `rings`를 96개로 두고 단면 방향 `ring_segments`만 8개로 제한한다. 원거리에서도 팔각형 경계가 아니라 매끄러운 원으로 읽히게 한다.

보급차량과 도로는 기본적으로 시각적 표현 또는 제한된 특수 시나리오 요소다. 일반 재보급을 위해 A* 차량 운행과 창고 간 재고 이전을 필수화하지 않는다.

## 19. 적 지식과 Raid Director

적 지식은 플레이어 방공망의 실제 객체 참조가 아닌 관측 보고로 구성한다.

보고 예:

- 추정 위치와 범위
- 관측된 장비 역할
- 확신도
- 마지막 관측시각
- 이전 공격에서 확인한 반응

확신도는 시간이 지나면 감소한다.

```text
confidence = max(0, confidence - decay_rate × elapsed_time)
```

Raid Director는 다음 입력으로 공격을 구성한다.

- 경과시간과 현재 공격 강도
- 사용할 수 있는 위협 콘텐츠
- 적 지식
- 최근 공격의 성공·실패
- 시나리오별 공격 역할과 제한
- 공격계획 전용 RNG

위협 Definition은 생성 반경·고도, 임무, 동일 목표 공유 여부와 적 지식·최근 방어 성과에 따른 선택 가중치를 공개한다. Raid Director는 위협 ID나 구체 Definition 타입을 분기하지 않고 이 데이터와 계약을 사용한다. 특정 자산 역할이 필요한 임무의 후보 판정도 자산 Definition이 공개하는 역할을 사용하며, 대레이더 공격처럼 관측이 전제인 콘텐츠는 필요한 적 지식 역할을 Definition에 명시한다.

공격 규모는 하나의 threat budget으로 관리한다.

```text
raid_budget =
    base_budget
    + time_growth
    + performance_adjustment
```

Director는 예산 안에서 정찰, 기만, 제압, 포화와 타격 역할을 조합한다. 정교한 범용 최적화기보다 설명 가능하고 테스트 가능한 archetype과 휴리스틱을 우선한다.

첫 시나리오는 12초 뒤 첫 공격을 계획하고 이후 레이드 기본 간격을 24초로 둔다. 75초 공격 구간 뒤에는 45초 회복 구간을 보장한다. 압력 단계는 90초마다 하나씩 오르고 레이드 간격은 단계당 0.6초씩만 줄여 최소 14초 아래로 내려가지 않는다. 위협 속도 배율은 20분에 걸쳐 증가하며 1.6배를 상한으로 한다. 이 값들은 `ScenarioDefinition`에 명시해 Director 내부 매직 넘버 없이 시나리오별로 조정한다.

같은 짧은 wave 목록을 반복하지 않되, 모든 공격을 완전히 무작위로 만들어 의도를 잃지 않는다.

## 20. UI와 표현 계층

`project.godot`의 `gui/theme/custom_font`는 `res://ui/fonts/NanumSquareB.ttf`를 가리킨다. Control의 기본 theme font와 `ThemeDB.fallback_font`를 사용하는 CanvasItem 직접 그리기 및 기본 Label3D가 이 저장소 자산을 공유한다. NanumSquareB에 없는 펼치기 삼각형 등 기호는 깨진 글리프 대신 표시되도록 FontFile의 시스템 fallback을 허용한다.

제품 진입점은 gameplay scene과 분리된 App Shell이다. App Shell이 메인 메뉴에서 모드를 확정해 gameplay scene을 생성하고, `Esc` 메뉴에서 세션을 일시정지하거나 gameplay scene을 폐기해 메인 메뉴로 복귀한다. 지속 작전 저장은 `Esc` 메뉴, 불러오기는 메인 메뉴와 `Esc` 메뉴에서 App Shell이 제공하며 전술 HUD에는 persistence 제어를 두지 않는다. 메인 메뉴 불러오기는 문서를 먼저 검증하고 저장 seed의 지속 작전 gameplay를 만든 뒤 snapshot을 복원한다. `Esc` 저장 시에는 일시정지 직전 속도를 문서에 보존하고, `Esc` 불러오기 뒤에는 복원된 속도를 기억한 채 메뉴가 닫힐 때까지 다시 일시정지한다. 게임 오버에서는 전면 입력 차단 Control이 다른 HUD와 월드 입력을 막고 App Shell도 `Esc`를 무시한다. 결과 화면의 재시작은 gameplay scene이 요청한 모드와 같은 seed 또는 새 seed를 App Shell에 넘겨 기존 gameplay 인스턴스만 교체하고, 메인 메뉴 요청은 gameplay를 폐기해 App Shell 초기 화면을 복원한다. HUD는 현재 모드의 전술 조작만 제공하며 실행 중 모드 전환을 소유하지 않는다. 준비 단계의 `StartButton`은 자산 카탈로그 바깥 HUD 하단 중앙에 있어 카탈로그 접힘과 관계없이 유지된다.

HUD 시간 제어의 네 `Button`은 toggle 상태를 현재 `GameSession.simulation_speed`에서 역으로 갱신한다. `statistics_changed`마다 0·1·2·4 중 일치하는 버튼 하나만 눌림 상태가 되고 전용 청록색 `StyleBoxFlat` 배경을 사용하며, 별도 `SpeedLabel`은 두지 않는다. 훈련 자동 정지·재생이나 저장 복원으로 속도가 바뀌어도 같은 갱신 경로를 사용한다.

상단 context menu는 열릴 때 `move_to_front()`로 HUD 루트의 마지막 형제가 된다. Godot의 Control 입력 순서는 `z_index`만이 아니라 형제 순서의 영향을 받으므로, 이 동작으로 메뉴의 시각적 전면 순서와 포인터 hit-test 순서를 일치시킨다. 방공 자산, 도시 상태와 위협 투입 메뉴는 같은 경로를 사용한다.

샌드박스 배치는 `PlacementController.selected` 또는 `selected_threat`를 지속 선택 상태로 유지한다. 성공한 좌클릭은 현재 후보 위치에 자산이나 위협을 생성한 뒤 preview와 선택을 정리하지 않으며, 우클릭·Esc·다른 배치 도구 선택만 명시적으로 취소한다. 위협 `OptionButton.item_selected`는 버튼 재확인 없이 `selected_threat`와 preview를 즉시 새 definition으로 교체한다.

제품 전술 UI는 플레이어 지식과 공개된 아군 상태만 소비한다.

- 미탐지 적 객체에는 전술 marker를 만들지 않는다.
- 항적 위치는 실제 객체 transform이 아니라 항적의 추정 위치를 사용한다.
- 분류 아이콘과 소속 색상은 현재 항적 판단을 사용한다.
- 관측 단절 상태는 opacity, 흔들림 또는 uncertainty 영역으로 표현한다.
- 화면 밖 marker는 항적의 추정 방향에서 계산하고, 도형과 선택 테두리가 잘리지 않는 20px 여백까지 viewport 가장자리에 붙인다.
- 선택 관계선은 공개된 센서 기여와 C2·교전 상태만 사용한다.

개발·디버그 표현은 실제 세계를 직접 볼 수 있지만 제품 UI와 명확히 분리한다. debug 표시가 제품 marker나 자동교전 데이터로 재사용되어 정보 누출을 만들지 않는다.

표현 계층은 다음 입력만 받는 것을 원칙으로 한다.

- 읽기 전용 상태 snapshot
- 위치와 상태 변화 event
- 발사, 폭발, 손상과 항적 변경 event

고도 프로파일은 3D 카메라 밖의 상·하 관계를 보완하는 좁은 2D 표현이다. 0–180m, 180–450m, 450–1500m를 같은 화면 높이의 저·중·고층 구간으로 나누고 실제 m 눈금을 함께 표시한다. 적성 정보는 플레이어의 공개 항적만, 아군 요격체는 플레이어가 소유한 실제 위치만 사용한다. 패널 폭은 유지하고 우측 화면 끝에서 44px 안쪽에 배치해, 화면 끝에서 20px 떨어진 방향 표식의 선택 테두리와도 겹치지 않는 간격을 둔다.

방공 자산 목록은 감시·추적, 지휘·지원, 미사일 방어, 근접·특수 요격의 역할 섹션으로 묶는다. 상단 `방공 자산` 버튼 아래에 최대 높이를 제한한 context panel로 열며, 콘텐츠가 적을 때는 실제 목록 높이에 맞추고 많을 때만 내부 목록을 스크롤한다. 각 구매 행은 자산명과 가격·해금 상태를 별도 Label로 양쪽 정렬하고 normal·hover·pressed·disabled 상태가 구분되는 공통 배경을 사용한다. 닫힌 상태에서는 전장을 가리는 잔여 panel이나 헤더를 남기지 않는다.

하단 feedback은 지속 조작 문맥과 일시 사건 알림을 분리한다. `PlacementController.feedback_changed`는 배치 가능 여부와 조작 지시는 지속 문맥으로, 배치 결과는 일시 알림으로 구분해 보낸다. HUD는 일시 알림을 3.5초 표시한 뒤 최신 지속 문맥으로 복귀하고 둘 다 없으면 Label을 숨긴다. 준비 화면은 방공 자산 배치와 방어 시작만 안내하며 전장 layout 이름이나 seed를 노출하지 않고, 일반 전투가 시작되면 지속 안내를 비운다.

카탈로그 자식 위의 휠 이벤트는 기본 `mouse_force_pass_scroll_events` 흐름으로 내부 `ScrollContainer`까지 전달해 목록을 움직인다. 카탈로그 외곽은 `MOUSE_FILTER_STOP`과 비활성화한 강제 스크롤 전달로 경계 입력을 viewport에서 끝내며, 카메라도 메인에서 등록한 UI 화면 사각형 안의 휠 입력을 추가로 거부한다. 카메라 방위각은 Q/E와 우클릭 수평 드래그로 바꾸고, 키보드 이동과 중클릭 이동 벡터는 현재 방위각을 적용해 화면 방향을 유지한다.

훈련 진입 예고는 깊이 검사와 원근 크기에 영향을 받는 3D 라벨이 아니라 도시에서 진입점까지 이어지는 점선 회랑, 화면 안전영역 가장자리에 고정한 화살표와 `훈련 표적 진입` 라벨로 표현한다. 안전영역은 항상 보이는 훈련 패널의 오른쪽 끝과 viewport 가장자리만 사용한다. 방공 자산 메뉴는 진입 표식 위치 계산에 참여하지 않으므로 열고 닫을 때 표식이 움직이지 않는다. 일반 화면 밖 항적은 고도 프로파일을 피해 안쪽으로 밀리지 않고 전체 viewport의 최소 가장자리 여백을 사용한다. 훈련은 방어 시작 시 방공 자산 메뉴를 닫고 지원 단계에서 다시 연다. 적성 잠정 항적만 있을 때는 자동 재생을 유지하고 확인 항적이 생겼을 때만 선택 단계로 전환해 일시정지한다. `PlacementController`는 지면 ray가 빗나간 좌클릭도 화면 좌표와 함께 선택 계층에 전달하고, `AirscainMain`은 화면 안 3D 표식과 화면 밖 전술 표식의 동일한 투영 위치를 사용해 항적을 고른다. 훈련 공격 UAV의 시작점은 도시 동쪽으로 전장 크기의 58% 떨어진 해상이며, 비행 표면을 기준으로 고도를 정한다.

VFX는 필요하면 pooling하고 동시 수를 제한한다. 화면에 보이는 효과의 수명이 gameplay 객체의 생명주기를 결정하지 않는다.

도시 건물 충돌은 생성 시 AABB를 캐시하고 64m XZ 셀에 건물 인덱스를 등록한다. 전체 도시 AABB를 벗어나는 선분은 즉시 제외하며, 선분이 지나는 범위의 셀 후보만 정밀 검사한다. 후보는 원래 인덱스 순서로 정렬해 동일 거리의 충돌 우선순위와 가장 가까운 접점을 보존한다. 기관포는 각 수치 적분 단계에서 표적 위치/속도를 한 번 읽어 탄들에 공유하며 생존 여부는 실제 피해 전에 계속 확인한다. 사격/공중폭발이 없는 기관포 런타임은 갱신하지 않고, 이미 투명해진 공중폭발 섬광은 렌더 목록에서 제외하되 잔연은 기존 수명대로 유지한다. 동적 탄막·연기 MultiMesh는 생성 때부터 custom AABB를 지정하고 CPU가 이미 아는 위치로 갱신해 경계 자동 계산의 GPU 읽기를 피한다. 선택 패널은 상태 행을 만들 때만 기본 스타일을 적용하고 경고 색상이 변할 때만 테마를 갱신한다.

추락 잔해는 격추된 객체의 가시 MeshInstance3D와 로컬 transform, 전체 기체 basis를 보존해 비행 중 기체와 같은 실루엣·크기·자세로 시작한다. 메시 리소스는 공유하고 원본 재질을 변경하지 않은 채 색상별 공유 그을음 재질을 사용한다. 비행/모델 생성 스크립트, 엔진 발광 메시·광원, 기존 입자와 표식은 복사하지 않는다. 앱 예열에 타격기의 추락 재질/메시 조합을 포함한다. 잔해는 최대 10초 비행하며 착지 시 기체를 숨기고 궤적 연기를 분리한다. 조류를 제외하면 예열된 ExplosionEffect 풀에서 반경 8의 섬광·광륜·충격파·짧은 광원·화구·연기·파편을 한 번 재생하고, 효과는 잔해 노드와 독립적으로 감쇠한다. 조류는 추락 연기와 착지 폭발 없이 원래 형상으로 떨어진다. 지면 판정은 잔해의 이전·현재 위치 선분과 실제 지형·건물의 가장 가까운 접점을 사용한다. 접점에서 이동과 연기 표본을 끝내고 폭발을 한 번 표시하며 추가 gameplay 피해는 주지 않는다. 전장 참조가 없는 독립 예열/검사만 전달된 고정 지면 높이를 사용한다.

Forward Mobile 환경은 HDR glow를 사용하되 일반 주광 재질이 번지지 않는 높은 threshold와 제한된 strength를 유지한다. 폭발·추진광·레이저 재질만 1보다 큰 emission multiplier로 bloom 입력을 만들며 실제 `OmniLight3D`를 짧게 병행한다. 레이저는 폭 없는 line primitive를 사용하지 않고, 길이에 맞춘 원통형 밝은 코어와 더 굵은 additive 광륜, 발사점·명중점 섬광으로 구성한다. 폭발은 섬광 구체 바깥에 짧게 팽창하고 사라지는 additive HDR 광륜을 겹친다. 시간에 따라 알파를 바꾸는 충격파 재질은 scene 공유 subresource를 직접 수정하지 않고 폭발 인스턴스마다 복제해, 새 폭발이 이미 감쇠한 다른 충격파를 다시 보이게 하지 않는다.

미사일 연기 궤적은 발사체 종료 시 월드 효과 부모로 재부모화하고 새 표본 생성을 멈춘다. 이후 가시 재질 알파와 그림자 재질 감쇠율을 같은 `smoothstep` 값으로 16초 동안 1에서 0까지 줄이고, 완전 투명 상태를 한 프레임 이상 유지한 뒤 정리한다. 폭발·손상·잔해의 `GPUParticles3D` 연기는 화면용 일반 알파 재질과 동일 입자 상태를 공유하는 그림자 전용 emitter를 함께 사용한다. 그림자 재질은 `SHADOWS_ONLY`로 일반 카메라 pass에서 제외하고 불투명 입자 표면만 shadow pass에 기록한다. 입자 수명 알파와 emitter 전체 감쇠율은 그림자 mesh의 국소 크기로 변환해 점 단위 Alpha Hash 노이즈 없이 연결된 윤곽이 연속적으로 수축한다. 따라서 화면 연기의 부드러운 투명도를 해치지 않으면서 지형 그림자도 같은 시간축으로 사라진다. `STRIKE_AND_EXIT` 도시 임무는 접근 시점에는 투하 상태만 확정하고, 실제 `air_strike_munition`이 지표 목표점에 도달할 때 `ProtectedObjective.apply_surface_impact()`로 피해와 연기 사이트를 함께 생성한다. 비행 중 공대지 탄의 현재·목표 위치, 속도와 피해량은 session snapshot에 보존한다. `Battlefield`는 시각 생성에 쓴 건물 transform을 단일 원본으로 보존하고 실제 box 크기의 AABB를 제공한다. 도시 목표는 gameplay RNG로 건물 하나를 고른 뒤 이름 붙은 X·Z 내부 범위와 높이 범위에서 각각 난수를 뽑는다. `AttackUav` 계열 중 물리 충돌로 임무를 끝내는 `IMPACT` 유형만 매 tick의 이전·현재 위치 선분을 모든 건물 AABB와 검사해 가장 가까운 접점에서 이동을 끝낸다. `RECONNAISSANCE`와 `STRIKE_AND_EXIT` 항공체는 건물 충돌로 임무가 취소되지 않으며, 이탈 단계에서는 `exit_point` 고도를 보존해 수평 경계에서 정지하지 않는다. 이탈 완료는 성공적인 임무 종료로 기록하되 폭발 VFX 없이 registry에서 제거한다. `ProtectedObjective`는 최대 네 개의 실제 충돌 위치와 source 높이를 한 사이트 데이터로 보존·저장한다. 피해 연기는 실제 충돌점에 고정된 단일 emitter만 사용하며, 30Hz 고정 시뮬레이션에서 좁은 상승 방향·완만한 횡풍·입자별 초기 크기 차이로 plume을 만든다. 건물과 아군 시설이 공유하는 `DamageSmoke` process material의 `scale_curve`는 정규화 수명 0에서 0.88, 0.68에서 1.16, 1에서 1.3으로 증가해 모든 손상 연기를 갑작스러운 팽창 없이 완만하게 키우며, 같은 process material을 쓰는 그림자 proxy에도 동일하게 적용된다. 고주파 turbulence와 위치가 다른 중·상부 emitter는 사용하지 않는다. 모든 인스턴스는 미리 최대 입자 용량을 가진 공용 process material을 사용하고 `amount_ratio`만 바꿔 최초 생성 시 GPU 재할당과 셰이더 생성을 피한다. `local_coords = false`인 입자는 충돌점부터 이어진 월드 공간 plume을 남긴다. 자산 상태 표식과 손상 연기는 공개된 탄약·가동·integrity 상태만 읽는다. 모든 `DefenseUnit`은 상태 표식보다 높은 위치에 작은 고정 화면 크기의 역할 아이콘을 유지한다. 감시·추적은 `◎`, 지휘·중계는 `◆`, 무장은 `▲`, 지원은 `■`로 표시하고 색도 역할별로 구분한다. 두 `Label3D`는 기존 글꼴 크기와 배치를 유지하며 `no_depth_test`와 높은 `render_priority`를 함께 사용해 투명 손상 연기 뒤로 가려지지 않게 한다.

고속 발사체와 추락 잔해의 연기는 Compatibility에서 지원되지 않는 `GPUParticles3D.emit_particle()`에 의존하지 않는다. 이전·현재 월드 위치 사이를 고정 거리로 표본하고, 공용 방사형 알파 billboard `QuadMesh`를 한 번의 draw call로 그리는 `MultiMeshInstance3D` 슬롯에 기록한다. 각 표본은 생성 시각과 위치뿐 아니라 결정론적으로 생성한 크기·농도·드리프트 편차를 보존해 가까이에서도 규칙적인 명암 띠가 생기지 않으며, 가시/그림자 셰이더가 공유하는 `trail_motion.gdshaderinc`에서 완만하게 커지고 떠오른다. 생성 시각·크기·농도는 INSTANCE_CUSTOM, 드리프트는 인스턴스 색상 채널에 한 번만 기록하며, CPU는 emitter 시간과 전체 감쇠 uniform만 갱신한다. 15Hz CPU 작업은 만료 슬롯 회수만 수행한다. 최대 팽창·드리프트를 포함한 custom AABB로 셰이더 이동이 프러스텀 컬링에서 잘리지 않게 한다. 가시 연기와 절반 밀도의 둥근 그림자 proxy는 같은 표본 알파와 emitter 전체 감쇠율을 공유하되, 그림자 표본은 고정된 홀짝 순서가 아니라 작은 묶음마다 위치를 분산해 반복 패턴을 피한다. MultiMesh는 생성 시 가시 인스턴스 수를 0으로 두고 실제 방출된 구간만 활성화하며, 수명이 끝난 슬롯은 활성 수명 목록에서 제거하고 재사용한다. 이 방식은 렌더 프레임 사이의 이동 거리와 무관하게 1m 단위 요격탄 궤적을 이어 주며, 네이티브와 Web에서 같은 구현을 사용한다. 아군과 적 미사일 모두 비행 종료 뒤에도 충분한 표본 수와 수명으로 궤적을 남긴다. 연기·불꽃·섬광은 공용 radial-alpha 카드를 사용하고, 방향성이 실제 형상인 추진 화염·예광탄·파편·채프만 mesh를 유지한다. 폭발의 짧은 광원은 연기 그림자와 별개로 실시간 그림자를 만들지 않는다. 추진 표현은 emissive material과 유한 범위 광원을 함께 사용한다. 타격기는 접근 임무 상태가 투하를 한 번만 시작하게 하고, 생성된 공대지 탄이 지표에 도달한 시점에 gameplay 피해와 명중 VFX를 함께 확정한다.

연기 VFX의 책임은 정책과 런타임으로 나눈다. `SmokePuffDistribution`은 seed 없는 serial 기반의 결정론적 표본 편차와 그림자 선택만 계산하고, `LingeringSmokeTrail`은 이동 구간 표본·MultiMesh 슬롯·수명만 관리한다. 연기 카드는 일반 알파 합성을 사용해 Compatibility의 depth pre-pass가 카드 중심만 가리고 가장자리를 중첩시키는 속 빈 명암을 만들지 않게 한다. `SmokeShadowFactory`는 GPU particle과 MultiMesh가 공유하는 둥근 그림자 proxy 및 재질을 생성하되, 모든 proxy는 `SHADOWS_ONLY`로 색상 pass에서 제외하고 조밀한 궤적은 가시 카드 한 변의 34%를 proxy 반지름으로 사용한다. 미사일 계열 궤적의 가시 pass는 공용 밝은 unshaded 재질로 색을 유지하고 방향광 그림자는 별도 proxy가 전담한다. `ExplosionTimeline`은 폭발 반경과 경과시간만 받아 핵심 섬광·광륜·카메라 방향 압력파·지면 충격파·광원의 크기와 알파를 계산하는 순수 정책이다. `ExplosionEffect`는 인스턴스별 재질, 방사형 카드 화구·연기·파편 시작과 노드 수명만 소유하며 additive 재질의 albedo와 emission을 같은 비율로 감쇠한다. 앱 셸은 64×64 독립 `CombatVfxWarmup`에서 요격체·폭발·피해 연기·에너지 효과·대응책·잔해·예광탄·장비와 위협 모델을 배치별로 렌더하고, 실제 draw 완료를 기다린 뒤 시작 버튼을 활성화한다. 피해 연기 호출자는 범용 `Node.call()` 대신 `DamageSmokeEffect` 타입 계약을 사용하며, 장면 기반 폭발·추락 효과는 typed node 참조로 의존성을 명시한다.

요격체는 `Battlefield`의 절차 높이장 셀 간격 절반 이하로 이전·현재 위치 선분을 표본하고, 높이 부호가 바뀐 최초 구간을 이분 탐색해 지형 접점에서 `지형 충돌`로 종료한다. 전장은 발사와 저장 복원 때 모두 다시 주입한다. 요격체는 원래 표적을 잃으면 발사 시 전달받은 공개 항적 중 확인·관측 단절 상태의 적성 항적을 평가한다. 탄종 적합도가 0보다 크고 탐색기 획득거리 600m 안이며, 예상 회전시간과 비행시간을 합쳐 남은 수명의 90% 안에 도달할 수 있는 후보가 있으면 거리·각도·탄종 적합도로 가장 나은 항적을 재획득한다. 대체 항적이 없거나 비행시간을 초과했을 때만 현재 위치에서 자폭한다. 대응책 기만이 성공하면 즉시 폭발하지 않고 플레어·채프의 고정된 허위 반사 위치로 유도된 뒤, 해당 지점을 지나 거리가 다시 증가할 때 유도 이탈로 종료한다. 근접신관이 작동하면 표적의 파괴 여부와 무관하게 요격체 폭발을 생성하므로 내구도가 높은 항공 표적에 비치명 피해만 준 경우에도 투사체가 단순 소실되지 않는다. 공중폭발의 연기·파편 초기속도는 전방향으로 분포시키고 중력은 이후 낙하에만 작게 작용한다.

`ThreatRegistry`는 등록된 위협이 제거될 때 신호를 보낸다. 요격탄은 제거 위치와 같은 분류의 후보 항적들을 비교해 가장 가까운 항적 하나에 먼저 상관한다. 상관 게이트는 고정 반경이 아니라 요격 반경과 해당 항적의 위치 불확실성으로 계산하며, 자신의 표적이 그 최인접 항적일 때만 이동 전에 대체 공개 적성 항적을 재획득한다. 파괴가 확인되지 않은 표적을 잃고 즉시 재획득하지 못하면 2.5초 유예 상태로 들어가 속력을 유지하면서 장비 본래 선회율로 50도 상승 방향을 향해 선회하고 연기 궤적을 이어가며 매 tick 후보를 다시 평가하고, 끝까지 없을 때만 보존한 `표적 소실`·`유도 상실` 원인으로 자폭한다. 원래 표적의 체력이 0 이하로 확인된 경우에도 같은 2.5초 재획득 유예를 적용하고 동일한 상승 선회로 매 tick 대체 표적을 계속 평가한다. 유예 안에 표적이 생기면 정상 유도로 복귀하고, 끝까지 찾지 못하면 별도 실패 문구 없이 공중 자폭한다. 상승 중 실제 다른 위협이나 지형과 만나면 기존 충돌 판정을 유지한다. 재표적화 시 기존 교전 예약은 해제하고 새 항적 예약으로 바꾼다. 실체가 없는 항적은 계속 교전할 수 있지만 요격탄이 유도점 45m 안까지 접근한 뒤 거리가 다시 증가하면 `유도 이탈`로 자폭해 고정점을 반복 선회하지 않는다. 탄종 적합도, 상관, 최소 접근 거리, 재획득 잔여시간·원인과 파괴 확인 후 종료 상태는 진행 중 요격탄 저장·복원에 이어진다.

대응책 성공 판정은 표적 정의의 플레어·채프 효과와 요격탄 탐색기 민감도 중 우세한 조합을 선택한다. 표적 뒤에는 해당 대응책 입자만 생성하고 내부 판정 문구는 표시하지 않는다. 채프는 방출 첫 프레임에 반경 20m 구체 안에 얇은 금속 박편 190개를 모두 분포시킨다. 초기 이동 속도는 0.05~0.3m/s, 중력은 0.1m/s² 미만으로 제한해 6초 동안 구름 범위가 실질적으로 퍼지지 않는다. 박편은 -180~180도 초기 각도와 양방향 회전속도를 무작위로 받고, 52개 반사점은 월드 위치별 위상이 다른 두 시간파를 결합한 셰이더로 짧고 불규칙하게만 빛난다. 탄약이 완전히 고갈된 자산의 월드 표식은 한 글자 약어 대신 화면 고정 크기의 `탄약 고갈` 문구를 사용한다.

건물과 자산의 피해 연기는 실제 타격점의 작은 상자형 방출면에서 부드러운 radial alpha billboard를 연속적으로 내보낸다. 도시 plume은 1,500개 버퍼와 18초 수명, 7.5~10.5m/s 초기 상승 속도, 7도 확산각, 아래쪽 중력 가속도와 수평 풍가속도를 사용한다. 발생 후 0.1초 안에 충분한 불투명도를 확보해 낮은 옥상에서도 기둥의 하단이 타격점과 분리되지 않게 한다. 따라서 입자는 하부에서 좁고 조밀한 기둥을 유지하고, 높아질수록 상승이 감속되면서 횡풍 변위가 누적된다. emitter 위치는 수명 동안 변하지 않으며 turbulence를 사용하지 않아 프레임마다 입자가 왕복하거나 떨리지 않는다. 높아진 입자가 조기 culling되지 않도록 `visibility_aabb` 높이를 220m 이상 보장한다. 화면용 billboard의 그림자 proxy는 평면 복제가 아닌 저해상도 `SphereMesh`를 사용해 사각 카드 모서리가 투영되지 않으며, 화면 emitter의 입자 수와 수명을 매 프레임 및 재시작 전에 동기화한다. Compatibility의 GPU 입자 `SHADOWS_ONLY` 누락을 피하기 위해 GPU proxy는 `ON`으로 렌더하고 셰이더에서 비그림자 패스를 버린다. 손상 자산은 연기와 별도로 `손상` 상태 표식을 노출한다. 런타임 emitter에는 `preprocess`를 사용하지 않고 최대 입자 버퍼를 scene에 미리 두어 피해 연기 생성 시 시뮬레이션이나 재할당이 한 프레임에 몰리지 않게 한다.

## 21. 저장과 복원

저장은 버전이 있는 plain-data 문서로 관리한다. scene tree 자체나 공유 resource를 그대로 저장 포맷으로 사용하지 않는다.

저장 대상:

- 시나리오와 전장 seed
- 세션 시간, 예산, 해금과 통계
- 배치 자산, 위치, 피해와 가동상태
- 탄약, 전력, 재보급과 수리 작업
- 실제 위협과 진행 중인 임무
- 플레이어 항적과 필요한 추적 상태
- 적 지식과 진행 중 공격계획
- gameplay RNG 상태

저장하지 않는 대상:

- 파티클과 일시 VFX
- UI 선택과 hover
- 재생성 가능한 terrain cache와 spatial index
- 디버그 표시

로드는 문서 버전과 필수 콘텐츠 ID를 검증한 뒤 현재 세션을 교체한다. 실패한 로드가 진행 중 상태를 부분적으로 변경해서는 안 된다.

`SessionSnapshot`은 섹션 구조, 콘텐츠 ID, runtime ID와 모듈 간 참조처럼 저장 문서 전체의 무결성을 검증한다. 자산·위협의 `content_state`와 방어 발사체의 고유 상태는 해당 `DefenseDefinition` 또는 `ThreatDefinition`이 검증한다. 새 콘텐츠는 자신의 저장 상태 계약을 Definition에 함께 구현하며 중앙 snapshot 검증기에 구체 타입 분기를 추가하지 않는다.

저장 스키마가 바뀌면 `CURRENT_VERSION`을 올리고, 읽을 수 있는 가장 오래된 버전을 `MIN_SUPPORTED_VERSION`으로 명시한다. 마이그레이션을 구현하지 않은 버전은 추정해서 부분 복원하지 않고 거절한다. 현재 버전은 21이며 16–20도 명시적으로 변환해 지원한다. 문서의 16→17 변환은 기존 상태를 보존한 복사본에 빈 자동 재보급 ID 목록만 추가하며 예전 작전을 자동 지출에 동의한 것으로 처리하지 않는다. 런타임 복원 전 `SessionSnapshot.migrate_content()`가 Definition의 `migrate_runtime_state()`를 호출해 17→18 콘텐츠를 변환한다. 기관포 Definition은 기존 탄약·교전규칙·난수 상태를 보존하고 빈 비행탄 목록을 추가한다. 18→19에서는 소유 자산 Definition의 공통 교전 방식으로 예약 종류를 부여하고 같은 근접방어 자산의 중복 예약은 잔여시간이 가장 긴 배정 하나로 합친다. 19→20은 도시 연기 지점에 현재 손상과 지점 수로 계산한 수리 기준을 부여하고, 이미 완전 복구된 도시의 구버전 잔류 지점은 제거한다. 20→21은 지원 작업의 수동 요청 여부를 추가하며, 출처를 알 수 없는 구버전 재보급은 완료음 없이 복원하고 수동 전용 수리는 완료음을 유지한다. 현재 저장은 지원 작업 요청 출처의 bool 형식, 도시 연기 수리 기준과 완전 복구까지 남는 마지막 지점, 예약 종류와 소유 자산의 일치·요격체 상한·근접방어 자산별 단일 배정, 자동 보급 목록의 탄약 자산 참조·정수 ID·중복과 기관포 탄별 비행·신관 상태를 검증한다. 쓰기는 임시 파일 검증과 기존 파일 백업을 거쳐 교체한다. 저장과 불러오기는 진행상태를 소유하는 지속 작전에서만 제공하고 훈련·샌드박스 상태는 지속 작전 저장에 섞지 않는다.

도시 피격 시 활성 연기 지점의 `repair_at`을 현재 기능부터 최대 기능까지 균등한 복구 단계로 배분한다. 마지막 지점의 기준은 항상 최대 기능이다. 수리로 기준에 도달한 지점은 기록과 emitter를 함께 제거·풀 반환하고, 남은 emitter와 그림자는 원래 건물 위치를 유지한다. 기준은 수리할 때 재계산하지 않아 작은 수리를 반복해도 진행이 누적된다. 새 피해가 발생하면 남은 지점과 새 지점에만 기준을 재배분하며, 완전 복구로 비운 옛 지점은 재피격 때 되살리지 않는다.

완전한 replay와 모든 플랫폼에서의 bit-identical 결과는 목표가 아니다. 다만 로드 직후 주요 gameplay 상태가 끊김 없이 이어져야 한다.

## 22. 성능 원칙

유지보수 경계는 구체적인 책임 단위로 둔다. `WreckAppearance`는 원본 모델의 가시 형상 복사·불필요한 광원/입자 제외·공유 그을음 재질만 담당하며 `FallingWreckEffect`는 낙하·접점·연기 분리·종료를 담당한다. `PlacementElevationGuide`는 전달받은 해발/경사 값을 표시하는 시각 노드이고, 배치 위치·유효성·등고선 상태는 `PlacementController`가 관리한다. 새 안내 표현이나 추락 재질을 변경할 때 전투/배치 로직을 수정하지 않는다. `EngagementCoordinator`의 예약 원본은 내부에 보관하며 외부에는 개수·항적별 조회와 독립된 저장 스냅샷을 제공한다. 예약 추가/제거는 인덱스 무효화를 포함한 공통 메서드만 사용한다. 새 범용 인터페이스·서비스 로케이터·상속 계층이나 저장 버전 변경은 필요하지 않다.

지형 가독성은 기존 높이·메시·충돌을 유지한 채 경사 기반 흙/암석 색과 완만한 명암 대비로 보강한다. 기본 20m 등고선은 약하게 유지하고 배치/재배치 후보 주변에서만 10m 등고선을 강조한다. 평탄면의 선과 화면 픽셀보다 촘촘한 선은 감쇠한다. TerrainMaterial은 월드 인스턴스별 리소스이므로 메뉴와 작전이 강조 상태를 공유하지 않는다. 배치 미리보기는 실제 설치점의 해수면 기준 높이와 주변 12m 표본의 지형 경사를 작은 화면 고정 Label3D로 표시한다. 옥상에서는 설치점 높이와 아래 지형 경사를 구분하는 `해발`/`지형 경사` 표기를 유지한다. 취소·지도 이탈·위협 투입 모드에서 등고선 강조를 해제한다. 추가 지형 메시나 텍스처 샘플은 사용하지 않는다.

교전 예약 목록은 저장과 시간 진행의 원본이며, 조회에는 항적별 총수/종류별 수·담당 자산 순서와 자산별 근접지원 예약 인덱스를 사용한다. 추가·표적 변경·해제·만료·복원 직후 인덱스를 무효화하고 다음 조회 전에 갱신한다. 동일 표적의 예약 시간 연장은 인덱스를 다시 만들지 않는다. 반환한 담당 자산 목록은 독립 배열이므로 호출자의 수정이 인덱스를 오염시키지 않는다. C2는 매 조회 때 자산 ID·위치·가동 상태를 보존 배열과 직접 비교해 임시 배열 해시 생성을 피하며, 이동/가동 변화의 즉시 감지와 기존 2초 재밍 갱신 주기를 유지한다. 가용 항적은 한 번 순회하되 로컬 항적 우선·공유 항적 후순위와 각 목록의 원래 순서를 보존한다. 항적 결과는 장기 캐시하지 않아 같은 단계의 새 관측도 즉시 반영한다.

기관포 근접신관 정밀 검사 전에 탄의 이동 거리·신관 반경과 표적의 최대 단계 이동 거리를 합친 보수적인 구로 먼 표적을 제외한다. 표적의 순서·안전시간·지표 충돌 우선순위와 실제 상대 선분 판정은 유지하며 빠르게 진입하는 표적도 후보에서 빠지지 않는다. 궤적 연기의 최종 알파가 정확히 0이면 vertex 단계에서 카드를 축소해 정리 대기 중 불필요한 픽셀 합성을 막는다. 만료 슬롯의 생성 데이터도 무효화해 billboard의 basis 재구성으로 옛 입자가 되살아나지 않게 한다. 입자 수·가시 알파 곡선·수명·그림자 정책은 줄이지 않는다.

`tools/combat_perf_check.gd`는 고정 seed의 기관포 CPU 작업과 24줄/19,200개 연기 갱신을 측정한다. `--render`는 실제 창에서 연기 나이를 6초로 고정하고, `--faded`는 15초로 고정해 감쇠 후 비용을 분리한다. `--no-smoke-shadows`는 그림자 비용 분리를 위한 진단 옵션이며 게임 설정이나 기본 그림자 품질을 바꾸지 않는다. 동일 옵션·해상도·렌더러에서 비교하고 테스트는 Dummy 오디오로 실행한다.

각 실제 전장은 `CombatEffectPool`의 폭발 8개와 도시 피해 연기 4개를 시작 전에 확보한다. 로딩 입력 차단막 뒤에서 실제 인스턴스의 GPU 버퍼뿐 아니라 폭발광을 받는 도시·지형 MultiMesh의 셰이더 조합까지 렌더한다. 준비 중에는 시뮬레이션을 진행하지 않는다. 폭발은 인스턴스별 재질과 입자 버퍼를 재사용하고 같은 World3D의 풀만 사용한다. 초기 용량을 넘겨 생성한 효과도 총 32개까지 풀에 보존해 재사용하고, 보존 한도를 넘는 효과는 생략 없이 일회성 생성한다. 섬광·광륜·충격파·광원은 기존 곡선의 알파/광량이 정확히 0이 되면 숨기며, 모든 단기 레이어가 끝난 뒤 타임라인·재질 갱신을 중단한다. 화구·연기·파편과 그림자는 기존 수명을 유지한다. 재사용 시 지연 압력파를 포함한 레이어 가시성을 초기화한다. 또한 저장 복원은 풀을 유지하고 활성 효과만 반납한다. 도시의 새 피격·복구·복원은 확보된 연기 슬롯을 순환 재사용하고, 자산은 배치 시 피해 연기를 확보한다. 화염은 고정 32개 버퍼의 `amount_ratio`로 강도를 조절하며 런타임 `preprocess`는 사용하지 않는다.

대표 공격에서 수십~수백 개의 물리 객체와 다수 VFX가 동시에 존재할 수 있음을 전제로 한다.

우선순위:

1. 단순하고 측정 가능한 구현
2. 병목 프로파일링
3. 필요한 영역만 최적화

예상 최적화 수단:

- 저주기 시스템 update 분리
- Godot group과 제한된 공간 query
- spatial hash 또는 grid
- 반복 건물의 `MultiMeshInstance3D`
- 미사일, 예광탄과 VFX pooling
- 멀리 있거나 중요하지 않은 표현의 LOD·update 감소

프로파일링 전부터 모든 객체를 pool로 만들거나 커스텀 ECS와 GDExtension으로 옮기지 않는다.

시뮬레이션 정확도는 카메라 거리 때문에 바꾸지 않는다. 표현 품질과 update 빈도만 안전하게 낮출 수 있다.

짧은 UI·전투 효과음은 동적 파일 로딩 없이 `preload()`한다. WebAudio는 압축 stream을 처음 sample로 재생할 때 등록 비용이 발생하므로 앱 로딩 중 전체 효과음을 sample로 미리 등록한다. 음원과 사건 매핑은 플랫폼 간 동일하게 유지하고, 실제 재생 백엔드만 Web에서는 sample, 이를 지원하지 않는 네이티브에서는 stream을 사용한다.

일반 미사일 2종과 소형 폭발 3종은 Ogg 자산 자체의 레벨을 보정해 각 그룹의 통합 음량을 약 −22.4 LUFS와 −22.2 LUFS로 맞춘다. 파일별 런타임 보정값은 사용하지 않으며, 음원의 길이·채널 구성과 무음·잔향 구간을 유지한다. 이 수치는 해당 그룹의 기준이며 다른 종류의 효과음에 일괄 적용하지 않는다.

## 23. 테스트 전략

앱 공통 설정은 `PlayerSettings` 타입의 `GameSettings` autoload가 소유하고 `user://settings.cfg`에 ConfigFile로 저장한다. 작전 저장 버전과 독립적이며 손상·잘못된 타입·비유한 수치는 기본값으로 대체하고 범위를 제한한다. `SettingsMenu`는 표시·입력만 담당한다. Master 아래 Missiles/Guns/Explosions/Alerts/UI 버스를 사용하며 기존 음원별 감쇠·기관포 대표 음성 예산·Web Sample 사전 등록은 유지한다. 기관포 발사·종료·자폭은 Guns, 접촉·탄약 부족·강도 변화는 Alerts로 보낸다. 카메라는 공통 감도를 적용하고 일시정지 메뉴에서 입력을 차단한다. 전체 화면은 네이티브 시작 시 복원하고 웹에서는 사용자 조작 시에만 요청한다.

### 단위 테스트

순수 계산과 상태 전이를 검증한다.

- 배치 판정
- 탐지 증거와 항적 생명주기
- C2 연결과 항적 가용성
- 교전 점수와 doctrine
- 탄약·전력·지원 queue
- 피해와 위협 결과의 단일 확정
- Raid Director의 예산과 선택 제한

### 통합 테스트

게임의 세로 흐름을 검증한다.

```text
실제 위협 생성
→ 센서 관측
→ 항적 생성
→ C2 공유
→ 방어체계 교전
→ 요격 또는 임무 성공
→ 피해·보상·통계 반영
```

기만 항적, C2 단절, 탄약 소진과 시설 손상도 작은 시나리오로 검증한다.

### 실행 검증

- headless 실행과 script 오류 확인
- 대표 scene smoke test
- 저장 후 복원 연속성 확인
- 실제 게임 창에서 카메라, 배치, UI와 VFX 확인

CLI는 별도 실행파일 환경변수 없이 `godot` 명령을 사용한다. 구체적인 검증 습관은 `AGENTS.md`를 따른다.

테스트를 위해 제품 코드에 전지적 정보를 노출하지 않는다. 필요한 진단 상태는 개발 전용 경계로 제공한다.

## 24. 기술적 비목표

다음은 기본 설계에 포함하지 않는다.

- 모든 gameplay 객체를 포괄하는 범용 ECS·Ability·Effect 프레임워크
- 실제 레이더 신호처리, 공력과 추진기관의 정밀 해석
- 패킷 단위 C2 네트워크와 통신 프로토콜
- 전력계통 조류 계산
- 차량별 물류 경로와 창고 간 원자재 시뮬레이션
- 모든 건물의 독립 물리·피해·복구 상태
- 파편 하나마다 생성하는 물리 projectile
- 저장 검증을 위한 canonical digest 체계
- 완전 결정론과 replay를 위해 모든 시스템을 재작성하는 구조
- 제품 코드와 분리되지 않은 전지적 debug UI

이 중 하나가 실제 gameplay 목표나 측정된 성능 문제를 해결하는 가장 단순한 방법일 때만 별도 설계로 추가한다.

## 25. 설계가 지켜야 할 최종 경계

다음 조건은 구현 세부사항이 변해도 유지한다.

1. 방어체계는 이용 가능한 항적 없이 숨은 실제 위협을 직접 공격하지 않는다.
2. 플레이어 UI는 실제 세계, 플레이어 지식과 적 지식을 혼합하지 않는다.
3. 적 공격계획은 플레이어의 숨은 실제 상태를 직접 읽지 않는다.
4. 게임 결과는 표현 계층이 아니라 시뮬레이션 상태에서 결정한다.
5. 콘텐츠 데이터와 개별 런타임 상태를 공유하지 않는다.
6. 한 상태에는 하나의 소유자만 둔다.
7. 새 콘텐츠는 공통 흐름에 조합되며 기존 콘텐츠 이름에 대한 분기를 요구하지 않는다.
8. 미래 기능을 위한 추상화는 실제 두 번째 사용 사례가 생긴 뒤 도입한다.
9. 현실성은 플레이어 선택과 시각적 설득력을 높이는 범위에서만 사용한다.
10. 현재 구현은 각 단계가 끝날 때마다 실행 가능하고 플레이 가능한 상태를 유지한다.
