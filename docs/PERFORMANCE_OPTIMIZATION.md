# 난전 최적화 후보

## 목적과 현재 판단

대규모 난전의 연산량을 **근처 후보 수, 변경된 상태, 화면에서 필요한 세부 표현**에 비례하도록 줄이는 것이 목표다. 첫 실험 후보는 **연기 그림자의 깊이 임포스터화**와 **기관포의 공간 후보 검색**이다. 그다음 C2 항적 조회 공유와 관측→항적 연관 검색을 검토한다.

근거는 [2026-09-10 병목 분석](PERFORMANCE_2026-09-10.md)과 [원본 측정 데이터](PERFORMANCE_2026-09-10.json)다. **기관포 공간 검색은 구현·검증해 채택했으며** [실제 결과](PERFORMANCE_IMPLEMENTATION.md)를 별도로 기록한다. 나머지 후보는 아직 미구현·미검증이며, 제외 실험에서 얻은 감소율은 실제 최적화의 예상 개선율이 아니다. 후보는 [SPEC](SPEC.md)·[TECH](TECH.md)의 확정 요구나 기술 선택을 대체하지 않는다. 판단 주기·표현 근사·플랫폼 경로가 달라지는 후보는 해당 계약과 함께 검토한다.

## 측정 근거

Godot 4.7.2, WSL/Mesa D3D12, Ryzen 7 5800X·RTX 3060, 실제 창 1600×900·MSAA 2× 조건이다. 주 제품 환경인 Windows 네이티브나 웹의 측정값으로 일반화하지 않는다.

1A와 1B는 서로 독립적인 실험 단위다. 기존 최적화에는 풀·예열·재질 공유·MultiMesh와 일부 조회 캐시가 이미 있다. 같은 기법을 추가하는 것만으로 남은 지속 부하가 줄어든다고 가정하지 않는다. 과거 무장 검색 인덱스 실험에서 전체 CPU 개선이 명확하지 않았으므로, 공간 검색은 이번에 확인한 루프를 대상으로 구축·갱신 비용까지 다시 측정한다.

## 1. 연기 그림자의 깊이 임포스터

현재 [SmokeShadowFactory](../effects/smoke_shadow_factory.gd)는 billboard 연기에 대응하는 작은 `SphereMesh`를 만들고, [SmokeShadowProjection](../world/smoke_shadow_projection.gd)은 이를 2048×2048 맵에 매 프레임 렌더한다. 맵에서 필요한 것은 빛 방향에서 보이는 표면의 깊이다.

**적용안:** 구형 메시를 두 삼각형의 사각형으로 교체하고, [그림자 셰이더](../effects/smoke_shadow.gdshader)에서 빛 방향으로 본 구의 원형 실루엣과 표면 깊이를 계산한다. 기하량을 줄이면서 현재의 깊이 기반 수신 구조를 활용하는 임포스터 방식이다. 단순히 검은 원을 그리면 연기보다 높은 건물에도 그림자가 생길 수 있으므로, 맵의 깊이 값과 proxy 사이의 깊이 판정이 일치해야 한다.

**검증:** 근접·원거리, 낮은 태양 고도, 건물 위·아래 연기, 중첩 입자, 팽창·드리프트·감쇠·완전 소멸을 실제 창에서 확인한다. 기존 저해상도 구와 완전히 같은 픽셀을 요구하지 않되 둥근 실루엣과 가림 관계를 확인한다. 같은 활성 표본으로 primitive, 맵 렌더 비용, 전체 프레임을 비교한다. 기하 감소가 fragment 계산이나 깊이 쓰기 비용 증가에 상쇄될 수 있다.

**큰 구조 변경 후보:** 입자별 그림자 대신 연기 덩어리 또는 궤적 구간을 대표하는 깊이·농도 표현을 쓴다. 가시 연기와 그림자의 표본 수를 분리할 수 있지만 농도 합성·높이·감쇠를 새롭게 정의해야 하는 표현 근사다. 화면 밖 연기라도 화면 안 지면에 그림자를 드리울 수 있으므로 caster 제외는 카메라 가시성만으로 판단하지 않는다. 정지 맵 재사용의 측정값은 이동 중인 연기 맵을 그대로 캐시해도 된다는 근거가 아니다.

## 2. 공간 분할과 Broad Phase

### 기관포와 요격탄

최적화 전 [GunfireRuntime._step()](../defense/close_in_gun/gunfire_runtime.gd)은 활성 표적의 위치·속도를 모으고 각 무장된 탄에 대해 전체 표적을 순회했다. 현재는 적분 단계별 공간 검색을 적용했다. 아래의 무기 간 공유와 요격탄 확장은 후속 검토 범위다. 거리로 정밀 검사를 건너뛰어도 후보 방문 비용은 남는다.

**적용안:** 위치를 기준으로 표적을 균일 격자 또는 공간 해시에 등록한다. 탄의 이번 이동 구간에 근접신관 반경과 표적 이동 범위를 포함한 보수적 영역을 질의하고, 수집된 후보에 기존 정밀 교차 검사를 실행한다. 고속 표적이 현재 칸 밖에서 진입하는 경우도 빠짐없이 포함해야 한다. 이처럼 빠른 후보 축소와 정밀 검사를 나누는 방식이 Broad Phase/Narrow Phase다. [NVIDIA의 충돌 후보 축소 설명](https://developer.nvidia.com/gpugems/gpugems3/part-v-physics-simulation/chapter-32-broad-phase-collision-detection-cuda)

격자를 탄·무기별로 다시 만들지 않고 공통 조회 구조로 유지한다. 생성·이동·소멸을 현재 게임 단계의 순서에 맞춰 반영하고, 후보 중복을 제거하되 기존 동률·명중 처리 순서를 보존한다. 검증 후 [요격탄 근접/기만 표적 검색](../defense/missile_battery/homing_interceptor.gd)에도 적용 가능성을 검토한다.

**검증:** 격자 경계를 지나는 탄·표적, 큰 delta와 고속 이동, 같은 단계의 생성·소멸, 도시 중앙 밀집, 빈 전장을 포함한다. 전수 검사와 후보·최종 명중 결과를 비교하고, 격자 구축·갱신·할당을 포함한 전체 비용을 잰다. 모두 가까이 몰린 상황에는 후보 축소 효과가 작을 수 있다.

### 관측과 항적 연관

[PlayerKnowledge._associate()](../tracking/player_knowledge.gd)에 별도의 항적 공간 검색을 적용한다. 관측 위치와 기존 동적 게이트로 후보를 찾고 현재 연관 규칙으로 최종 항적을 결정한다. 예측 위치, 관측 공백에 따른 게이트 확대, 같은 센서·시각의 중복 배제와 동률 순서를 유지한다.

센서 관측을 합친 직후 항적 위치가 바뀌면 같은 스캔 안의 다음 관측 검색에도 반영해야 한다. 삭제·새 항적 생성·예측 이동도 갱신 대상이다. **실제 위협용 공간 자료와 플레이어 항적용 공간 자료를 분리**해 미탐지 기체의 실제 위치나 ID가 연관·자동교전의 지름길로 쓰이지 않도록 한다. 다양한 공간 분할은 조회를 줄이는 대신 이동 갱신 비용과 메모리를 요구한다. [Spatial Partition](https://gameprogrammingpatterns.com/spatial-partition.html)

## 3. C2 조회 공유와 시간적 일관성

### 변경 감지 캐시

[C2Network.available_tracks_for()](../c2/c2_network.gd)는 각 무기의 요청마다 로컬·공유 항적을 필터링하며 캐시 조회 전 endpoint 상태를 확인한다. 공통 연결망과 항적 기여 정보를 이용해 재사용 가능한 부분을 준비하고, 무기별 로컬 우선순위와 고유 조건을 적용하는 방안을 검토한다.

무효화 조건에는 연결·재밍·가동 상태·이동·센서 기여·항적 생명주기가 포함된다. 게임 단계 안에서 변경된 정보가 다음 요청에 보이도록 하며, 기존 재밍 갱신 정책도 보존한다. 가용 항적 목록의 캐시와 위치·속도·우선순위 점수의 캐시를 구별한다. 변경되지 않은 부분을 재사용하는 것이 목표이며, 임의의 유효 시간 동안 오래된 결과를 반환하는 방식은 별도의 근사다.

**검증:** 로컬/공유 목록 순서, 연결 단절·복구, 재밍, 항적 소실, 센서 추가·제거, 같은 단계의 변경을 기존 조회와 대조한다. `get_active_tracks()`를 포함한 앞단 배열 생성과 캐시 갱신 자체의 시간·할당을 함께 측정한다.

### 표적 유지와 재평가 분리

[MissileBattery.gameplay_tick()](../defense/missile_battery/missile_battery.gd)의 지속적인 조준과 전체 후보 재선정을 분리한다. 현재 표적을 따라 조준하면서 관련 사건 또는 정해진 판단 시점에 재선정하는 방식이다. 발사 직전에는 표적 유효성·사거리·고도·탄약·교전 예약을 현재 상태로 다시 검사한다.

정확한 변경 감지와 달리 재평가 빈도 축소·표적 유지 성향은 반응시간, 표적 전환, 사격 기회에 영향을 줄 수 있다. 기존과 같은 결과를 보장하는 캐시 최적화와 구별해 교전 정책으로 검토한다. 상태가 유효하다는 이유만으로 더 긴급한 표적의 출현을 무시하지 않도록 한다.

## 4. 지역별 배칭·LOD·표현 예산

### 지역별 배칭과 UI

현재 궤적별로 사용하는 MultiMesh를 여러 효과가 공유하는 지역별 버퍼로 모으고, 개별 생성 시각·크기·감쇠 상태를 인스턴스 데이터로 전달하는 방안을 검토한다. 재질 공유와 제출 횟수 감소가 목적이다. 한 버퍼의 범위가 지나치게 커지면 일부만 보여도 전체를 그릴 수 있으므로 지역별 가림과 투명 정렬을 함께 설계한다. [Godot MultiMesh 최적화](https://docs.godotengine.org/en/stable/tutorials/performance/using_multimesh.html)

UI는 변경된 데이터만 갱신하고 같은 종류의 표식·재질을 가능한 범위에서 묶는다. [고도 프로파일](../ui/altitude_profile.gd)의 원/외곽선과 다각형/외곽선 조합이 구체적인 조사 대상이다. CanvasLayer 전체 제외의 454 draw 감소를 고도 프로파일 단독 비용으로 간주하지 않는다. 정보·표시 순서를 유지하며 그리기 제출과 상태 갱신 비용을 각각 측정한다. [Godot GPU 최적화와 배칭](https://docs.godotengine.org/en/stable/tutorials/performance/gpu_optimization.html)

### 화면 크기 기반 LOD와 효과 예산

가까운 연기는 개별 입자로, 멀리 보이는 연기는 적은 표본·궤적 리본·대표 덩어리로 표현하는 후보다. 거리뿐 아니라 화면에서 차지하는 크기를 기준으로 삼고 전환 구간의 팝핑·명암 변화를 확인한다.

동시 폭발의 실제 광원·파편·부차 효과에 전역 예산을 두고 화면상 중요도에 따라 배분할 수도 있다. 피격·요격 결과를 읽는 핵심 표시는 보존해야 한다. 카메라 밖 효과의 표시 비용을 줄여도 전투·탄도·탐지 시뮬레이션을 중단하지 않는다. LOD·효과 예산은 표현 정책 변경이며, 기존 효과를 같은 품질로 더 빠르게 그렸다고 보고하지 않는다.

### 연기만 저해상도로 렌더한 뒤 합성

부드러운 연기를 작은 별도 버퍼에 렌더하고 주 화면에 합성한다. 깊이 정보를 사용해 건물·지형과의 가림을 유지해야 하며, 경계의 halo·연기 누출과 깊이 전달·추가 패스 비용을 검증한다. 선명한 파편이나 UI까지 같은 방식으로 낮출 필요는 없다. [GPU Gems의 저해상도 입자 렌더링](https://developer.nvidia.com/gpugems/gpugems3/part-iv-image-effects/chapter-23-high-speed-screen-particles)

주 화면 해상도 0.5배 실험에서 개선이 없었던 만큼 순수 픽셀 비용만 주원인이라고 가정하지 않는다. 그림자 기하·제출 구조를 먼저 정리하고 Compatibility에서 깊이·합성 경로를 실제 구현했을 때의 총비용을 측정한다.

## 5. 스캔 분산·다중 갱신 주기·고정 tick

**Time Slicing:** 레이더별 스캔 간격을 유지하면서 시작 위상을 분산해 같은 순간에 스캔이 몰리지 않게 한다. 총연산 감소보다 p95와 최대 지연 개선이 목표다. 최초 탐지 시점, 관측 결합, 레이더 추가 배치·저장 복원의 위상에 영향을 줄 수 있으므로 검증한다. 큰 스캔을 여러 프레임으로 나눌 경우에도 관측 시각과 결과 적용 시점을 명확히 해야 한다.

**다중 갱신 주기:** 이동·충돌, 표적 판단, 지원망, UI에 필요한 갱신 빈도를 구분하고 화면의 이동·회전은 보간한다. 탐지와 표적 판단 빈도는 Definition과 정책을 기준으로 정하며 성능을 위해 임의의 수치를 확정하지 않는다. 관측·교전 신선도와 빠른 위협에 대한 반응이 검증 대상이다.

**고정 tick과 따라잡기 한도:** [현재 루프](../main/main.gd)는 받은 시간을 최대 1/30초 단계로 전부 나눠 처리한다. 긴 프레임 뒤에 더 많은 게임 단계를 처리하면서 지연이 커질 수 있다. 고정 시뮬레이션과 렌더 보간을 분리하고, 계산 여유와 따라잡기 한도를 정의하는 구조를 검토한다. 한도 초과 시 게임 시간을 늦출지 등 시간 정책이 필요하며, 시간을 조용히 버려 부하를 낮추지 않는다. [Fix Your Timestep](https://gafferongames.com/post/fix_your_timestep/)

고정 50ms 진단은 이 실시간 피드백을 직접 측정하지 않는다. 실제 자동 루프에서 1×·2×·4×, 긴 프레임 주입, 일시정지·재개, 저장 복원과 장기 실행을 확인한다. 물리 시간 단위 변경은 탄도·근접신관·발사 간격의 결과와 함께 검증한다.

## 6. 데이터 배치와 후순위 실행 경로

### 연속 배열과 공통 표적 데이터

[기관포 런타임](../defense/close_in_gun/gunfire_runtime.gd)의 탄 위치·속도·수명·상태를 연속된 typed 배열에 두고 일괄 처리하는 후보다. 표적 위치·속도의 반복 수집과 임시 배열도 공유 가능한 범위를 조사한다. Dictionary 접근·할당·흩어진 데이터 접근을 줄이는 방향이며 전체 게임의 ECS 전환을 요구하지 않는다. [Godot CPU 최적화](https://docs.godotengine.org/en/stable/tutorials/performance/cpu_optimization.html)

배열에서 제거할 때 인덱스가 바뀌는 문제, 안정적인 ID, 탄 처리·피해 적용 순서, 저장 문서 변환을 검증한다. 같은 단계의 표적 생성·소멸·이동을 공유 데이터가 올바르게 반영해야 한다. 공간 검색 이후 남은 루프 비용을 기준으로 도입 순서를 정한다.

### GDExtension과 작업 스레드

후보 축소와 데이터 정리 후에도 비싼 순수 계산이 남으면 해당 루프만 GDExtension으로 옮기는 방안을 검토한다. 배열을 묶어 전달해 호출 경계 비용을 제한하고 기존 Resource·scene 구성과 저장 계약을 유지하는 방향이다. 플랫폼별 빌드·배포 비용과 경계 호출·데이터 변환 비용까지 측정한다.

작업 스레드는 읽기 전용 상태를 받아 독립 계산하고 메인 스레드가 정해진 순서로 결과를 반영하는 구조를 후보로 삼는다. 결과 대기·복사 비용, 실행 중 상태 변경과 늦은 결과의 폐기 정책이 필요하다. 활성 SceneTree를 작업 스레드들이 직접 조작하는 방식은 안전하지 않다. [Godot 스레드 API 지침](https://docs.godotengine.org/en/stable/tutorials/performance/thread_safe_apis.html)

### 렌더러 비교

주 대상인 Windows 데스크톱에서 같은 부하를 Compatibility와 Mobile/Forward+로 비교할 가치는 있다. 변경만으로 빨라진다고 가정하지 않으며 재질·연기·그림자·조명·예열을 실제로 확인한다. 현재 Godot 웹 렌더링은 Compatibility를 사용하므로, 공통 경로를 유지할지 플랫폼별 경로를 둘지에 따른 유지보수 비용도 포함한다. 스택·렌더러 변경은 별도 작업으로 다룬다. [Godot 렌더러 비교](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html)

## 실험 단위와 채택 기준

1. **1A 단독:** 같은 연기 표본으로 구형 proxy와 깊이 임포스터를 교차 비교한다. primitive 감소와 별도로 맵·전체 프레임 시간을 확인하고 실제 그림자를 검증한다.
2. **1B 단독:** 전수 검사와 격자 후보 검사를 동일 입력으로 비교한다. 후보 누락·명중 결과·처리 순서를 확인하고 격자 관리까지 포함한 전체 CPU를 측정한다.
3. **C2와 항적 검색을 각각 적용:** 캐시 또는 연관 후보 변경을 한 번에 하나씩 적용해 결과와 비용을 분리한다.
4. **남은 병목 재측정:** 배칭·데이터 배치·시간 분산·표현 정책·실행 경로 변경은 새 비용 분포에 따라 순서를 정한다.

각 실험은 기존 진단기의 기본/대형 CPU와 실제 창 부하로 비교한다. 자세한 [재현 명령과 표본 정의](PERFORMANCE_2026-09-10.md#재현-명령)를 사용하며 성능 실행끼리는 동시에 돌리지 않는다. 평균·p95·최대, 원본 프레임/단계 추적, 개체·항적·탄수와 최종 상태를 기록한다. 렌더는 예열·해상도·카메라·시각 상태를 맞추고, 전후 기준 및 역순 반복으로 변동을 확인한다.

규칙 보존 후보는 관련 단위/통합 회귀와 비교 입력에서 결과를 확인한다. 표현 변경은 실제 게임 창에서 근접·원거리·중첩·감쇠를 확인한다. 초기 표적 생성 때의 지연도 측정하며 안정화 구간 통계와 분리해 남긴다. 첫 고정 seed에서 유효한 후보만 추가 seed·밀집/분산·야간·장기 부하와 실제 Windows 네이티브·웹으로 검증 범위를 넓힌다.

개선은 관리 비용을 포함한 전체 지표에서 반복 확인되어야 한다. 품질·반응시간·배포 복잡성이 달라졌다면 그 변화도 결과에 명시한다. 특정 FPS나 제외 실험의 감소율을 달성 조건으로 미리 약속하지 않는다.
