# 난전 최적화 구현과 검증

기준 분석은 [2026-09-10 측정](PERFORMANCE_2026-09-10.md), 검토할 기법은 [최적화 후보](PERFORMANCE_OPTIMIZATION.md)다. 아래는 실제 구현·측정 결과이며 제외 실험의 예상 감소율을 적용한 수치가 아니다.

## 전체 적용 전후

## 기관포 공간 후보 검색

`GunfireRuntime`은 각 적분 단계에서 표적 위치를 64m 3차원 격자에 넣고, 탄 이동 구간에 신관 반경·최대 표적 이동 거리를 더한 영역만 조회한다. 표적이 64개 이하거나 조회할 칸이 표적 수보다 많으면 전수 검사를 사용한다. 후보를 원래 등록 순서로 정렬해 동률 피해 순서를 유지하고 기존 상대 선분·안전시간·표면 충돌 판정을 적용한다. 비행탄 없이 폭발 잔상만 남았을 때에는 표적 자료를 수집하지 않는다.

격자는 탄별로 만들지 않고 해당 적분 단계의 모든 탄이 공유한다. 현재는 포대 사이에 장기 캐시하지 않는다. 앞선 무기·피해 신호에서 일어나는 생성·제거와 다음 적분 단계의 위치·속도 변화를 기존 시점 그대로 읽기 위한 범위다. 전역 공유에는 이 변경들의 명시적 무효화 계약이 추가로 필요하다.

## C2 공유 항적 조회

`PlayerKnowledge`의 관측 생성·수정, 생명주기 변경, 삭제·초기화·복원에 revision을 부여한다. `C2Network.available_tracks_for_knowledge()`는 같은 revision에서 가용 항적 배열을 한 번 만들고, 도달 가능한 센서 목록과 로컬 센서 목록이 같은 무기들의 필터 결과를 공유한다. topology 변경과 기존 2초 재밍 갱신 때 공유 결과를 무효화한다.

캐시는 소유자인 `PlayerKnowledge`의 변경 경로를 따르는 실제 무기 조회에 적용한다. 임의 배열을 받는 기존 `available_tracks_for()`는 즉시 필터링하는 API로 유지한다. 반환 배열은 복사하므로 호출자의 배열 수정이 다른 무기에 영향을 주지 않으며, 내부 항적 참조는 현재 위치·속도·품질을 계속 읽는다. 로컬 우선 순서·목록 안의 순서와 기존 갱신 시점을 보존한다. revision은 각 생명주기/복원 signal 전에 바뀌어 같은 호출 스택에서 조회해도 적용된 상태를 읽는다.

## 관측과 항적의 공간 연관 검색

`TrackSpatialIndex`는 플레이어의 추정 위치만 XZ 격자에 넣는다. 항적마다 관측 공백으로 커지는 연관 게이트를 덮도록 128m부터 두 배씩 커지는 격자 중 하나를 고른다. 질의는 각 사용 중인 크기에서 인접 9칸을 찾는다. 큰 게이트의 항적 때문에 모든 질의 반경을 크게 만들지 않으면서, 최종 3차원 거리 판정에 필요한 후보를 포함한다.

예측·삭제 뒤에는 다음 질의에서 재구축하며 관측으로 변한 위치·게이트와 새 항적은 signal 전에 즉시 반영한다. 후보를 원본 배열 순서로 정렬해 복원된 ID가 뒤섞여 있어도 기존 동률 결과를 유지한다. 분류·같은 센서/시각 중복·엄격한 거리 게이트의 최종 판정은 기존 규칙이다. 64개 이하, 미래 시각 관측의 추가 예측, 비정상 게이트 설정은 전수 경로로 처리한다. 저장에는 격자를 넣지 않는다.

| 별도 상세 관측 처리 전체 | 6.801ms | 4.090ms |

대형 네 실행씩의 평균은 **44.626→44.118ms, 약 1.1% 감소**다. 추가 두 쌍은 각각 0.436ms, 2.254ms 줄었으나 최초 두 실행 평균에서는 수정판이 약 0.329ms 느렸다. 전체 CPU 효과는 작고 환경 편차와 겹친다. 연관 검색 자체의 약 51% 감소를 전체 게임 개선율로 주장하지 않는다. 별도 상세 전체 CPU도 43.460→43.454ms로 거의 같았다.

41,827개 관측에서 후보 방문은 **8,870,718→1,852,740회로 약 79.1% 감소**했다. 구축·갱신·정렬을 포함한 해당 검색 비용 감소, 추가 교차 실행의 전체 CPU 감소, 아래 전수 대조를 근거로 채택한다. CPU 전체의 큰 개선으로 간주하지 않으며 다른 항적 밀도에서의 관리 비용은 계속 비교 대상이다.

대형 비교의 최대 접촉 364·항적 303·기관포 탄 158, 최종 접촉 206·항적 143·도시 기능 8520은 모두 같다. 기본도 최대 186·120·53, 최종 110·38·9250으로 같다. 발사체 부모의 잔류 효과 수는 실제 경과 시간에 따라 달랐다.

### 규칙 검증

두 seed의 3센서 × 96관측 × 18단계에서 기존 전수 검색과 매 관측의 선택 항적 및 매 단계의 전체 저장 가능한 항적 상태를 대조했다. 이동·분류 증거·관측 잡음·미래/과거 시각·삭제·초기화와 원본 배열을 뒤집은 복원을 포함한다. 별도 공간 검색은 300항적·300질의의 동적 게이트 후보 포함성, 음수 경계·격자 크기 전환·소실·재활성·생성·삭제를 검증한다. 같은 호출 스택의 관측 callback에서 새 위치와 새 항적이 보이는지도 확인했다.

공간 인덱스·탐지 추적·C2 단위 합계 26개 / 20,296개 단언을 통과했다. 전체 회귀에서는 훈련 메뉴를 닫으면 1배속이 된다고 기대하던 단언 하나가 기준 `f598d16`에서도 실패함을 독립 재현했다. 훈련은 정지 상태로 시작하므로 기존 정지를 복원하는 기대값으로 수정했다. 게임의 훈련·메뉴 동작은 바꾸지 않았다. 수정 후 **전체 26개 스크립트·420개 테스트·60,944개 단언**을 통과했다.

## 연기 깊이 임포스터: 제품 적용 보류

구형 proxy를 두 삼각형으로 바꾸고 빛 카메라의 직교 ray와 구/타원체의 교차로 실루엣·표면 깊이를 계산했다. 인스턴스의 비균일 축척·회전, 궤적 이동·팽창·감쇠를 반영하며 계산한 깊이를 실제 깊이 버퍼와 RGB 맵에 함께 기록한다. Compatibility의 깊이 좌표는 [Godot 공식 문서](https://docs.godotengine.org/en/stable/tutorials/shaders/advanced_postprocessing.html)의 OpenGL NDC 규약을 따른다.

**기하량은 줄었지만 안정적인 프레임 개선을 확인하지 못해 게임은 기존 구형 proxy를 유지한다.** 구현은 `tools/smoke_shadow_experiment.gd`와 셰이더에만 보존하고 제품의 효과 팩토리·궤적 구성에는 연결하지 않는다.

### 동일 정지 난전의 ABBA 비교

실제 창에서 대형 고정 공습 400단계를 진행한 뒤 시뮬레이션·표현 노드와 GPU 입자를 정지했다. 같은 146개 proxy 노드의 입자 버퍼·재질 uniform·카메라·맵 크기를 유지하며 구형→임포스터→임포스터→구형 순서를 두 번 반복했다. 각 구간은 10프레임 예열 뒤 30프레임이다.

| 반복 | 구형, 앞 / 뒤 구간 평균 | 임포스터, 두 구간 평균 | 반복 내 두 방식 평균의 차이 |
| --- | ---: | ---: | ---: |
| 1 | 126.365 / 163.535ms | 155.916 / 156.982ms | 임포스터 약 7.9% 느림 |
| 2 | 158.068 / 150.329ms | 166.943 / 109.705ms | 임포스터 약 10.3% 빠름 |

draw는 양쪽 2031, primitive는 **1,893,148→471,654로 약 75.1% 감소**했다. 전체 구간 평균은 구형 149.574ms, 임포스터 147.387ms로 약 1.5% 차이지만 반복별 방향이 반대이고 구간 편차가 훨씬 크다. 이를 성능 개선으로 채택하지 않는다. `DEPTH` 쓰기와 추가 fragment 계산이 기하 감소를 상쇄했을 가능성은 있으나, 이 측정만으로 GPU 내부 원인을 확정하지 않는다.

이 실험 빌드의 고정 공습 프레임 평균은 369.630ms/p95 645.872ms였다. 과거 391.052ms와는 실행 시각·표현 상태가 다르고 기관포 변경도 포함하므로 임포스터 개선율로 사용하지 않는다.

### 정확도와 재현

실제 게임 창의 연기 지면 그림자·소멸 캡처가 통과했다. 별도 `smoke_depth_check.gd`는 96분할·48링 기준 구와 임포스터를 실제 렌더해 원형, 회전·비균일 축척, 중첩, 낮은 빛 각도, 궤적 드리프트, 감쇠, 완전 소멸의 7개 조건을 비교한다. 경계 차이는 최대 12픽셀, 캡처 RGB 깊이 차이는 최대 0.001208이었다. RGBA8 캡처의 양자화 허용 범위 내 비교이며 비트 단위 동일성이나 임의 건물/시점의 완전한 품질 동등성을 보장하지 않는다.

```bash
godot --audio-driver Dummy --path . --script res://tools/smoke_depth_check.gd
godot --audio-driver Dummy --path . --script res://tools/profile_check.gd -- --large --render --compare-smoke-proxies
```

`--compare-smoke-proxies`만 사용하면 게임 계산 중 매 단계의 draw를 기다리지 않는 빠른 도구 검증이 가능하지만, GPU 입자의 시간 경과가 달라 위 실제 공습 장면과 비교하지 않는다. 일반 실행에는 실험 proxy를 적용하지 않는다. 다른 드라이버나 더 큰 표본에서 다시 검토할 수 있으나 현재의 기하 감소만으로 프레임 개선을 가정하지 않는다.

제품 복구 뒤 실험 전용 옵션의 실제 창 실행도 완료했다. 빠른 도구 검증 조건은 518개 proxy 노드, 2863 draw, 구형 4,303,975/임포스터 797,395 primitive였다. 구간 평균은 구형 327–350ms, 임포스터 301–380ms였고 이 조건에서도 반복별 개선 방향이 달랐다. 위 400 draw 공습의 장면과 합산하지 않는다. 최종 도구 check-only·메타데이터 생성과 오류 검사도 통과했다.

## 재현 명령과 범위

```bash
# 전체 회귀
godot --headless --audio-driver Dummy --path . -s addons/gut/gut_cmdln.gd -gdir=res://tests -ginclude_subdirs -gexit
# 계측 없는 대형 CPU와 별도 중첩 비용
godot --headless --audio-driver Dummy --path . --script res://tools/profile_check.gd -- --large
godot --headless --audio-driver Dummy --path . --script res://tools/profile_check.gd -- --large --breakdown --detail
# 추가 seed·야간·60초 게임 진행
godot --headless --audio-driver Dummy --path . --script res://tools/profile_check.gd -- --large --night --seed=90210 --seconds=60
# 실제 창, 오디오 출력 없음
godot --audio-driver Dummy --path . --script res://tools/profile_check.gd -- --large --render
```

`--seed`와 `--seconds`를 생략하면 종전 73129·20초 그대로다. 실제 단계 수는 50ms 단위로 내림하며 `PROFILE_CONFIG`에 seed·단계 수·주야간·부하 크기를 기록한다. 배치 및 위협 구성은 같은 seed와 옵션으로 재현한다. 상세 타이머를 켠 실행은 원인 분석용이고 계측 없는 실행과 섞어 평균을 내지 않는다. 성능 실행끼리나 전체 회귀와 동시에 돌리지 않는다.

## 남은 병목과 후속 우선순위

모든 CPU 변경을 포함한 상세 대형 실행은 평균 43.454ms / 50ms 게임 진행이었다. 중첩 구간은 부모에 포함되므로 아래 행을 합산하지 않는다.

| 남은 구간 | 평균 시간 | 다음에 줄일 작업 |
| --- | ---: | --- |
| 미사일 포대 3종 합계 | 12.810ms | 공통 항적 특성·탄종 평가의 중복 계산 |
| 그 안의 미사일 표적 선택 | 6.350ms | 9,600회 선택 / 입력 항적 1,633,030개 |
| 기관포 전체 / 내부 탄도 | 8.092 / 5.160ms | 탄의 Dictionary 접근·표적 자료 수집·적분 |
| 레이더 2종 합계 / 내부 연관 검색 | 6.321 / 2.876ms | 실제 탐지 후보·가림 판정과 잔여 연관 관리 |
| 여러 무기 안의 C2 가용 조회 | 1.404ms | 연결 즉시 확인 0.831ms, 필터 자체는 0.171ms |
| 전술 UI 갱신 | 0.043ms | 현재 CPU 우선순위는 낮음 |

다음 규칙 보존 후보는 **표적 특성의 같은 단계 내 공유와 기관포 탄 데이터의 연속 배열화**다. 고도·분류·속도 등 항적별 계산과 무기별 탄약·교전 예약 조건을 분리해야 한다. 발사 직후 탄약과 예약이 달라지는 만큼 선택 결과 전체를 장기 캐시하면 안 된다. 배열화도 탄 제거·피해 신호·저장의 기존 순서를 보존해야 한다. 이 두 후보는 이번에 구현한 것으로 보고하지 않는다.

화면 지연에는 여전히 **연기·입자·그림자 표현**이 크다. 깊이 임포스터의 단순 기하 감소는 채택 근거가 부족했다. 다음 렌더 작업은 Windows 네이티브·WebGL의 같은 장면에서도 병목을 확인하고, 동일 재질의 효과를 지역 단위로 모아 제출 횟수를 줄이는 방법을 비교하는 것이다. 가림 경계와 투명 정렬을 유지하는지 먼저 확인해야 한다. 더 큰 감소가 필요하면 연기 덩어리/궤적 구간별 집계 그림자, LOD·효과 예산·저해상도 합성을 별도 표현 정책으로 설계한다. 이들은 그림자·효과 수를 그대로 유지한 이번 CPU 최적화와 구분한다.

긴 프레임을 현재 루프가 전부 작은 단계로 따라잡는 구조는 유지했다. 고정 tick·보간·따라잡기 한도는 게임 시간과 1×/2×/4× 배속 계약을 먼저 정해야 한다. GDExtension·작업 스레드·렌더러 전환도 현재 측정으로 자동 채택하지 않는다. 이번 고정 단계 CPU/실제 창 비교는 자동 실시간 루프의 배속별 FPS, Windows 네이티브 또는 WebGL 성능을 검증한 결과가 아니다.
